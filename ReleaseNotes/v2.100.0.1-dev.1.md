## 新增

- **下载服务 C# 契约库与传输引擎**（`PCL.Download`，netstandard2.0 / net10.0 双目标）：
  定义 `IDownloadEngine` 与下载请求、选项、进度等 DTO；实现多源并发下载（HttpClient 多源
  failover）、Range 分片与断点续传、服务端不支持 Range 时降级为单流、SHA1/MD5 校验、
  已有文件跨版本复用、全局限速令牌桶、自适应追加分块，以及进度上报与取消令牌。
  附 xUnit 单测 11 项（以 TcpListener 假服务器模拟 Range、限速、Range 违约、断连行为），当前全部通过。
- **C# 引擎接入 VB 编排层**（`NetInterop.vb`）：文件下载在首线程时机由 CAS 抢占后交由
  C# 引擎执行，引擎负责多源 failover、分片、合并与校验；进度镜像回 VB 侧
  （`NetFile.DownloadDone`、`NetManager.DownloadDone`、`FileSize`、下载中状态）；
  完成回写 `File.Finish()`，失败分发 `Source.Ex` 后走既有 `OnFileFail` 汇总；
  用户取消时联动取消引擎 CTS。引擎启动失败会自动撤销抢占并回退 VB 原实现。
- **代号（发布通道）体系**：按《分支与发布规范》区分 `dev` / `slush` / `alpha` / `beta` / `pc` /
  `snapshot` 六种代号。代号名、显示名、版本号段、遥测策略、提示文案与制品名统一由
  `ModBuildChannel` 提供，编译期常量由 CI 按分支注入，不再由「构建配置」决定代号。
- **版本号按号段表分配**：`base = 5000 + 100 × 周期序号`，号段按代号阶梯严格递增——
  `dev = base+0…9`、`slush = base+10…19`、`alpha = base+20…59`、`beta = base+60…89`、
  `PC = base+90…94`、`SP = base+95…99`，保证全局单调递增。
- **MC 下载功能恢复**：开关由编译期常量下移为部署期配置，支持环境变量 `PCL_ALLOW_MC_DOWNLOAD`
  与启动器同级的 `DownloadPolicy.ini`，并随产物分发配置样例。
- **关于页独立化**：新增「关于 pcl-next」「当前版本」「项目进度」「作者与贡献」四个区块，
  明确区分本项目与上游 PCL；上游作者龙腾猫跃、HerobrineXia 保留署名与赞助入口
  （依 PCL 分发有限许可），并标注为「上游 PCL 作者」。

## 重写

- 主程序由 .NET Framework 4.8 迁移到 **.NET 10**（`net10.0-windows`），改为 SDK 风格工程，
  发布形态为 **自包含单文件**（`pcl-next.exe`），目标机无需安装任何 .NET 运行时。
- 第三方依赖统一改走 NuGet（CacheCow 2.13.1、NAudio 3.3.0、Imazen.WebP 11.0.0、
  ThrottleDebounce 2.0.2、Newtonsoft.Json 13.0.3），移除原先「内嵌 DLL + `AssemblyResolve`」
  的动态加载机制；删除 Ookii.Dialogs.Wpf 与 System.Net.Http.Formatting。
- 工程目录由 `Plain Craft Launcher 2` 更名为 `pcl-next`，程序集名、窗口标题、
  打包 URI 与内联 XAML 的 `assembly=` 引用同步更名。
- `PCL.Download` 的 `HttpRequestCodeException` 更名为 `HttpStatusCodeException`，
  避免与 `MeloongCore` 中的同名类型在全局导入后产生歧义引用。
- **下线内置自动更新模块**：pcl-next 没有自己的更新服务器，沿用上游的更新通道只会指向
  PCL 官方源、误导用户下载到别人的包。因此移除 `--update` 自更新启动参数、`UpdateRestart` /
  `UpdateReplace` / `IsUpdateWaitingRestart` / `DownloadLatestPCL` 等接口与「下载正式版 PCL」
  的整合包导出逻辑；「检查更新」改为打开本项目的 GitHub Releases 页面。

## 修复

> 以下缺陷均为**开发与自测过程中发现**的（并非用户在 GitHub 提交的 issue），
> 按《分支与发布规范》§5.4 的要求一并记录。

- **社区资源加载器全部失败**：.NET Core 起 GBK / GB18030 等代码页需显式注册，
  否则简体中文转换会抛 `NotSupportedException`（This system does not contain support for
  the GB2312/GBK encoding），表现为下载页的 Mod / 整合包加载器直接 `Failed`。
  处置：启动时调用 `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)`。
- **命中 HTTP 缓存的请求整体失败**：CacheCow 存下的是已解块正文，响应头却仍带
  `Transfer-Encoding: chunked`，读回时会按分块格式解析正文并抛
  `InvalidOperationException`（Error parsing HTTP message header byte N），
  表现为 BMCLAPI 兜底源的加载器 `Failed`。处置：新增 `ResilientCacheStore` 装饰器，
  写入前移除 `Transfer-Encoding`，读取异常时删除该条目并按未命中处理。
- **旧版 HTTP 缓存目录无法读取**：CacheCow 2.13 无法解析 net45 时代写下的缓存文件，
  沿用旧目录会抛异常使请求直接失败。处置：缓存目录切换到 `Cache/HttpV2`。
- **帮助页加载报未知类型 MyCard**：程序集改名时只替换了打包 URI 的 `;component` 前缀，
  漏掉内联 XAML 中的 `clr-namespace:PCL;assembly=`，共 10 处。处置：全部改为 `pcl-next`。
- **单例检查失效**：FindWindow 使用的窗口标题未同步更名。处置：补上 `pcl-next`。
- **自动更新残留清理不完整**：清理列表未包含更名后的 `pcl-next.exe`。处置：补上。
- **dev 与 slush 版本号相同**：两个内部代号共用 `base-1` 号段，从 slush 切回 dev 时会被
  判成「版本倒退」而误弹降级提示。处置：按新号段表为每个代号分配独立递增区间，
  并新增 `SystemHighestSlushVersionReg` 设置项，避免两个内部代号的「历史最高版本号」
  互相覆盖。
- **下载 C# 引擎全源连接挂起时的静默卡死**：真机 NeoForge 26.3.0.99 安装卡在 2%、0 B/s
  约 90 秒、日志零输出。根因：某镜像响应异常，所有源连接在超时后进入 `OnChunkFailure`
  的非禁用路径——该路径既不打日志也不打警告，调度器静默换源循环重试，用户视角等于卡死。
  处置：非禁用路径补 Warn 日志（源 / 失败次数 / 异常）、成功开启分块时补日志（对齐 VB 行为）、
  连接超时的 `OperationCanceledException` 转义为明确的 `TimeoutException`、
  `DownloadOptions` 新增 `MinConnectTimeoutMilliseconds`（默认 15000，对齐 VB）；
  并补充回归单测（两源均连接挂起 → 必须超时换源、留痕、最终明确失败）。

## 已知问题

- **本版本是 .NET 10 迁移与 C# 重写过程中的中间产物**，主程序行为与 2.99.0.1 正式版存在差异：
  - 启动器**没有内置的自动更新模块**：上游 PCL 依赖自带的更新服务器，而 pcl-next 没有自己的
    更新源，因此已把更新通道整体下线——「检查更新」改为直接打开本项目的 GitHub Releases 页面，
    升级需手动下载新版本。
  - 资源子系统、下载 UI、整合包与游戏启动等模块仍是 PCL2 的 VB 实现。
  - 整合包导出不再向整合包内塞入「下载来的正式版 PCL」，改为在正式通道下直接复制当前运行的
    启动器本体（dev 通道下则不附带 PCL）。
- 下载服务刚切换到 C# 引擎，仅有单测覆盖，**尚未经过真实网络环境的充分验证**。
  遇到下载异常时请附上 `PCL/Log1.txt` 反馈。
- dev 版与正式版的配置、注册表相互隔离，可与 2.99.0.1 正式版并存；
  建议在升级前备份 `%APPDATA%\.PCL\` 下的配置目录。
- dev 版不上传遥测。
- **构建期仍有大量 CA1416 平台兼容性警告**（数千条，集中在上游 PCL2 遗留代码调用的
  Windows 专有 API 上）：不影响编译产物与运行，但属于 .NET 10 迁移的技术债，
  需在后续 C# 重写中逐项消除。
