## 重写

本版是 **Phase 3 的收官版**，并把 Phase 4 从「首步」推进到「数据源全通、只剩编排」。

**承接 dev.3 的顺延契约**：dev.3 发布时把 Phase 3 拆成两半——「可离线验证」的搜索 / 版本解析 / 本地扫描
随 dev.3 发布，「需要联网与真机」的联网半边整体顺延。本版补齐的就是后者，**plus 负债两代的真机验证**。
契约兑现情况逐项如下：

| dev.3 顺延项 | 本版落地 |
|---|---|
| `IResourceProvider` 抽象 | 工程查询 / 批量查询 / 版本枚举 / 指纹反查 / 搜索分页五个方法统一到 `IResourceProvider`；双站融合与 `IsLike` 去重**平移复用** dev.3 的 `ResourceSearcher`，未重写 |
| CF / Modrinth API 客户端 | `CurseForgeProvider` / `ModrinthProvider`：分页、429 退避、错误分类（网络 / 超时 / 4xx / 5xx / 429 / 解析）与既有模型对齐 |
| 请求签名与候选源 | `ResourceSourceResolver`（官方 + MCIM 多镜像候选顺序、逐候选超时，逐字对齐 VB `DlModRequest`）、`ResourceSigning` + `RequestSigningHandler`（UA / Referer / `x-api-key` / `{CDN}` 标记） |
| CF API Key 降级 | Key 只读环境变量 `PCL_CURSEFORGE_API_KEY`，**禁止硬编码**；缺失时裁掉 CF 源、给出可展示文案、由 Modrinth 承接，**不抛错中断**；镜像域不泄漏 Key |
| `LocalResourceOnlineLoad` | `LocalResourceOnlineLoader`：指纹反查（CF Murmur2 / Modrinth SHA1）→ 工程回填 → 更新检测 → 下载源合并 → 6 小时缓存时效 |

**Phase 4 首步**：下载页（Mod / 整合包 / 资源包 / 光影 / 数据包五类）的搜索与列表数据源由 VB 的
`ResourceSearcher.Run` 改为 C# 侧 `ResourceProviderRegistry.Search`。融合、去重、排序仍在 C# 的
`ResourceSearcher` 里单点实现，registry 只做「源收敛 + 入口收敛」——这是刻意的：同一套排序逻辑
存在两份必然会漂移。

**Phase 4 主体（本版新增三块数据源）**：

| 块 | 原实现 | 现在 |
|---|---|---|
| MC 版本清单 | VB `DlClientListMain` 三路取数 + 手工 JSON 解析 | `McVersionManifestClient`：三档源排期、特供版本合并、Drop 分组全部在 C# |
| 资源详情页 | VB `ResourceVersion.FromProjectId` 直连 CF/MR | `PCL.Download.ResourceVersion.FromProjectId`：工程查询 → 版本枚举 → 依赖补全，VB 只做 DTO 投影 |
| 六类加载器列表 | VB `ModDownload` 的六个 `*Main`，各自拼正则、各自排期、各自缓存 | `LoaderListClient`：统一竞速、统一缓存、统一解析；VB 侧只保留 `LoaderTask` 外壳与结果投影 |

加载器列表这块的迁移量最大，也最容易被低估：六类列表里有四种取数形态——OptiFine 官方页是 HTML、
镜像站是 JSON；Forge 的 MC 版本列表官方是 HTML、镜像是 JSON 数组；Forge 版本列表官方是 HTML 表格、
镜像是有 `files` 数组的 JSON；NeoForge 干脆是「两段原文拼起来做正则」。此外还压着三处历史包袱
（Forge 的「司马版本」分支补全与 1.7.10 分支注入、LiteLoader 的 `1.8` / `1.9` 文件名补 `.0`），
全部**照原样平移**，没有趁机「顺手改对」——这些行为决定已装实例能不能被反查到。

迁移后 VB 侧净减 435 行（+107 / −542），六类列表的调用方（安装页、实例重构、整合包安装反查）零改动。

## 优化

- **429 与 5xx 走冷却换源，4xx 立即失败**：资源站的 429 是最常见的失败模式（曾把镜像打到全线 0 B/s）。
  下载侧早已用「冷却而非重试」解决，资源侧沿用同一原则，并新增「4xx 不换源」——换源对
  「工程不存在」「参数非法」这类错误没有意义，只会白白多打几次请求。
- **翻页状态收敛到一处**：C# 侧 `SearchResult` 同时承载两站的偏移、总量与跨页去重状态，
  VB 列表只是它的镜像。页面重建 `Storage` 时引用自然清空，等价于原先的「重新搜索」语义。
- **跨文件共享并发预算**：多文件同时下载时共用同一份 `ConcurrencyBudget`，避免各文件各自开满并发
  触发限速（表现为总速度骤降到几十 KB/s）。
- **降级提示只说一次**：源可用性由环境变量决定、进程内不变，因此提示条在页面首次加载时判定一次，
  不在每次搜索时重复弹出。
- **候选源竞速收敛到一处**：`McVersionManifestClient` 里内嵌的「按时刻依次启动 / 先成功者胜 / 已启动的全部失败
  就立刻切下一个」的轮询，被提成 `SourceRace` 供版本清单与六类加载器列表共用。两套调度各写一份必然漂移，
  而这类漂移的症状（某个源的切换早/晚几秒）几乎不可能靠人工回归发现。
- **加载器列表的进度不再「卡在第一个源」**：旧 VB 实现里，如果先启动的源直接失败，会一直等到下一个源的
  排期时刻（最坏 60s）才换源；现在改为「已启动的源全部失败 → 立即启动下一个」。这是 dev.2 起下载侧
  failover 的同一条原则，加载器列表此前没享受到。

### 其他修复

- **dev.3 发布的 exe 实际不含引擎修复**（重要）：dev.3 发布时，14:10–16:55 那整轮下载引擎改进
  （7 文件、+1304 行）只存在于工作区、从未提交，而标签构建用的是干净 worktree。结果线上
  `2.100.0.3` 仍会复现「NeoForge 卡 2% / 16%」「速度掉零后不再补分块」「进度 NaN%」。
  本版已把这批改动纳入版本库并进标签构建：分块失败指数退避、429/503 主机冷却、读停滞超时独立于
  连接超时、首包对冲（主源无首包则并行请求备源、先到者胜）、死源快判、慢源自动换源续传、
  `MaxChunksPerHost` 约束单镜像并发、进度镜像改原子交换并允许负增量。
- **宿主从未注入 `ResourceApi.Default`**：C# 侧所有联网方法（Provider、在线反查、`FromProjectId`）
  都经 `ResourceApi.Resolve` 取默认请求器，未注入时直接抛「未注入 IResourceApi」——
  也就是说联网半边即便代码齐全，真机上一条请求也发不出去。现在启动时注入
  `ResourceSigningOptions.Default` 与 `HttpResourceApi`，失败只告警、不中断启动。
- **`DelegatingHandler` 的同步 `Send` 路径不经过 `SendAsync`**：只重写后者会让 UA / `x-api-key`
  全部丢失（`HttpResourceApi` 用的是同步 `HttpClient.Send`）。密钥类问题，由新增单测抓出。
- **CF `exactMatches` 的 file 对象缺 `gameId`**：`ResourceVersion.FromPlatformJson` 按 `gameId`
  存在性判别平台，缺失时会被误判成 Modrinth 并丢掉加载器标记。Provider 侧补了注入。
- **CF 工程列表退化成「每工程拉全量版本」**：保留 `latestFilesIndexes` 参与解析，
  否则 `CurseForgeFileIds` 与 Drops 只能靠全量版本接口补齐，一页 40 个工程就是 40 次请求。

### 迁移期发现（加载器列表）

- **直连通道只有 JSON，HTML 列表会被误判成「官方源坏了」**：`IDirectResourceApi` 只返回已解析的 JSON 节点，
  而 OptiFine 官方页与 Forge 版本列表页是 HTML。若硬走 JSON 通道，解析阶段就会抛 `Parse` 异常并被当作源失败
  而切到镜像——表面上「能用」，实际是官方源永远拿不到数据。已新增 `IDirectTextResourceApi`（只搬字节不解析），
  并把 `HttpResourceApi` 的单次请求拆成「传输 + 错误归类」与「JSON 解析」两层，两条通道共用前者。
- **「installer 优先于 universal」这条规则此前没有任何用例守着**：反向验证（把优先级改坏看用例会不会失败）时发现，
  原夹具里 installer 与 universal 从不同时出现在同一个版本条目里。这条规则错了不会报错，只会让 1.6.x 的部分版本
  下到 `universal.zip`——安装时表现为找不到安装器。已补同一版本同时挂两类文件的夹具与用例，两个数组顺序各一条。
- **迁移中误删三个加载器入口**：`DlOptiFineListBmclapiLoader` / `DlFabricApiLoader` / `DlOptiFabricLoader`
  在替换区域时被连带删掉。编译期即报「未声明」被抓到，已补回；其中 OptiFine 那个改走单镜像源入口
  （`FetchOptiFineMirror`），因为实例重构与整合包反查需要「全量且稳定」的清单，而官方页会删旧预览版。

## 已知问题

- **在线反查的 C# 实现「已就位、未接管」**：`LocalResourceOnlineLoader` 已通过单测，但 Mod 管理页的
  「更新检测」仍走 VB 实现，用户实际感知与 dev.3 一致。接管属于 Phase 4 主体剩余部分，顺延 dev.5。
- **下载 UI 的编排层仍由 VB 驱动**：本版把**数据源全部切到了 C#**（MC 版本清单、资源详情页、六类加载器列表），
  但安装流程编排（`ModDownloadLib`）、任务列表与进度仍是旧实现。Phase 4 的完整退出标准顺延 dev.5。
- **六类加载器列表本版只做到「单测 + 反向验证 + 编译通过」，未逐类真机安装冒烟**：20 个用例覆盖了
  六类的解析、数量下限回退、候选源切换、缓存与取消，反向验证也确认了用例真的在守逻辑；但每一类
  真正装一次（尤其 NeoForge 的 `47.1.82` 不可下载判定、LiteLoader 的 `1.8` / `1.9` 文件名）仍待真机确认。
  若某类列表条目异常，请附 `PCL/Log1.txt`——切换候选源与胜出源都有日志留痕。
- **启动器没有内置的自动更新模块**：上游 PCL 依赖自带更新服务器，pcl-next 没有自己的更新源，
  已把更新通道整体下线——「检查更新」改为打开本项目 GitHub Releases 页面，升级需手动下载。
- **整合包导出不再附带「下载来的正式版 PCL」**：改为正式通道下复制当前启动器本体（dev 通道不附带）。
- dev 版与正式版的配置、注册表相互隔离，可与 2.99.0.1 正式版并存；
  建议升级前备份 `%APPDATA%\.PCL\`。dev 版不上传遥测。
- **构建期仍有大量 CA1416 平台兼容性警告**（数千条，集中在上游 PCL2 遗留代码调用 Windows 专有 API）：
  不影响编译产物与运行，属 .NET 10 迁移技术债，需在后续重写中逐项消除。
