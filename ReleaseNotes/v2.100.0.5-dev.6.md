## 重写

### 1. 架构裁决：Phase 4 退出口径采用 A（2026-11-08，用户确认）

《计划-Phase4主体》§4.9 原本写的是「安装编排的 `LoaderBase` 生成改为 C# 输出」。按字面执行会撞上
架构护栏：`PCL.Download.csproj` 声明 `<PclIsGuiFree>true</PclIsGuiFree>`，禁止内核引用 WPF /
`pcl-next`；而 `LoaderBase` / `LoaderTask` / `LoaderCombo` 定义在 VB 主工程 `ModLoader.vb`（791 行）
且带 UI 事件。内核无法产出它，除非先把状态机下沉——那正是排在 Phase 6 之后的 T2 拆壳。

**裁决内容（唯一真源：《计划-Phase4收尾与Phase6下线》§0.1）**：

- 采用 **口径 A**：C# 输出**全部编排决策与任务描述符 DTO**；VB 只做「DTO → `LoaderBase` 树」的
  **无逻辑装配**，执行 lambda 仍在 VB。`LoaderBase` 状态机**不**下沉，公开签名不改。
- **Phase 4 完成判据（正式文本，取代「C# 生成 `LoaderBase`」）**：
  「**UI 行为不变（含禁用态）、进度 / 取消 / 重试正确，且安装步骤的顺序 / 权重 / Block / Show /
  下载清单与任务描述符全部由 C# 决定**」；装配层不得出现 `If 组件已选 Then …` 形式的业务判定。
- **口径 B（提前 T2）未采纳**；T2 拆 `PCL.Core` 仍排在 Phase 6 之后，不因本裁决提前。
- 生效范围仅 Windows 线 `dev.6-Windows`；Linux / Android 线各自维护规则文档。

后续不得以「C# 没产出 Loader」为由重开 Phase 4。《计划-Phase4主体》§4.9 已改标为「已移交」。

### 2. P4-A：编排决策 DTO 全集

本轮只改 `PCL.Download` 内核与 `PCL.Download.Tests`，**VB 主工程零改动**，用户可见行为无变化。

| 文件 | 内容 |
|---|---|
| `InstallTaskDescriptor.cs`（新增） | `InstallLoaderKind` / `InstallCancelSemantics` 两个枚举、`InstallTaskDescriptor` 只读描述符、 `InstallTaskDescriptors` 规格工厂、`InstallTaskPlanner.Describe` 装配入口 |
| `InstallPlan.cs` | `InstallPlanStep` 挂上装配规格（`Task` / `Inputs` / `Outputs` / `SubSteps` / `DownloadKinds` / `Cancel` / `ReportsProgress` / `SubStepsSource`）；`InstallPlanRequest` 补 `HasMinecraftJson`；`Build` 末尾统一注入带请求上下文的规格，**现有 15 个字段语义与所有 Block / 权重布尔式零改动** |
| `InstallDownloadPlan.cs` | 新增 `NetFileDescriptorKind`（13 类）、`NetFileDescriptor.Kind` / `SimulateBrowserHeaders`；`InstallDownloads` 从 1 个工厂扩到 13 个，把 VB 里散落的 `New FileChecker With {…}` 校验口径收编为可单测的单一真源 |

描述符只含基元 / 字符串 / 集合 / 枚举，不引用 `McInstance` / `MergeJson` / `MyListItem` /
`NetFile` / `LoaderBase`；子加载器骨架逐字对齐 `McDownloadClientLoader`（9–69 行）与
`McInstallLoadersGet`（1766–1770 行）。OptiFine / Forge / NeoForge / LiteLoader / Fabric 五个复合体的
内部子列表仍由宿主 VB 函数提供，已在 `SubStepsSource` 登记函数名，供 P4-B 逐类下沉。

**下载清单的校验口径逐类对齐**（举例）：原版 json / 资源索引按 JSON 校验；原版 jar
`MinSize=1024 + sha1 + size`；OptiFine 安装 300 KB、另存为 64 KB；Forge 带 Hash 而 NeoForge 不带；
Fabric API / OptiFabric 带 `SimulateBrowserHeaders=True`。这些差异写错不会编译报错，只会静默下到错误页。

### 3. P4-B 批次 1：顶层薄装配层

口径 A 落地到 VB 侧。新增 `pcl-next/Modules/Download/LoaderPlanAdapter.vb`（243 行，
`Partial Public Module ModDownloadLib` 的一部分，共享原 Module 的 `Private` 宿主函数）；
`McInstallLoadersGet` 由 196 行缩到 91 行（−137 / +31），装配段整体移交 Adapter。

| 变化 | 说明 |
|---|---|
| 步骤存在性 | 原 7 处 `If 组件已选 Then` 归零，改为遍历 `InstallTaskPlanner.Describe(Plan)`，`Select Case D.Kind.Value` 分派到 13 个具名 `Assemble*` 方法 |
| 决策来源 | 名称 / 权重 / Block / Show 各 13 处一律读 DTO；OptiFine 双形态由 `SubStepsSource` 分派、「是否记入安装清单」由 `Outputs` 判定；「补全文件」两个副加载器读 `SubSteps` |
| P4-A 接线 | `InstallPlanRequest.HasMinecraftJson` 由 VB 显式传入，C# 据此决定 `Client` 是否插入「获取原版 json 地址」子步骤 |
| 执行层 | `McDownloadClientLoader` / `McDownloadForgelikeLoader` / `MergeJson` 等宿主函数与内联 lambda 原样保留，`LoaderBase` 公开签名零改动 |

本批为**等价重构**，无用户可见行为变化；内核与测试工程零改动。
**明确未完成（P4-B 批次 2）**：OptiFine / Forge / NeoForge / LiteLoader / Fabric 五个复合体内部子列表
与 `Client` 子列表仍由 VB 宿主函数提供（`SubStepsSource` 已登记函数名，需逐类下沉）；
资源详情页与 `ResourceVersion` / `ResourceProject` 只读投影收尾也未动。
UI 行为等价性**尚未经真机回归**。

## 优化 / 修复

- **修复 NeoForge 26.3.0.101 安装器报「no minecraft installation」**：`RequestTaskTempFolder()`
  返回以 `\` 结尾的目录，包进命令行引号后拼出 `<dir>\"`，被 `CommandLineToArgvW` 解析成字面引号，
  安装器拿到的 gameDir 不存在。新增 `InstallerArguments.QuoteDirectory` 统一去尾斜杠，
  Forge / NeoForge 与 OptiFine 的 gameDir / user.home / jlw.tmpdir 一并收编。
- **修复安装器 Java 版本选择**：旧口径 `AtLeast(8,0,60)` 按 JavaList 顺序取首个通过者，
  原版 26.3 要求 Java 25 却会选到列表靠前的 Java 21。现从原版 json 读
  `javaVersion.majorVersion`，≥22 时先精确匹配该主版本，本机没有才放宽为「不低于要求」；
  读不到字段仍回退 `≥8`，老版本行为不变。
- 新增 26 个守门用例（含变异反证），全量单测 **567 / 567 通过**。
- P4-A / P4-B 批次 1 本身仍是 DTO 增量与等价重构，无用户可见行为变化。
- 真机 GUI 安装 `26.3-NeoForge 26.3.0.101` 仍待回归，详见《经验与踩坑》④。
