## 重写

本版的主体是**把资源子系统里可离线验证的三块能力从 VB 平移到 C#**，行为与 VB 逐一等价
（包括上游若干刻意的古怪逻辑）。全部落在 `PCL.Download`（net10.0，不反向依赖主工程）。

- **统一哈希模型（`HashType` + `HashHelper`）**：此前传输层按「十六进制串长度猜算法」，
  资源侧另有一套 CF 指纹逻辑。现在收口为一个 `HashType` 枚举（MD5 / SHA1 / SHA256 / SHA512 /
  MurmurHash2），CurseForge 指纹复用同一实现。为什么改：资源识别必须让「下载校验用的哈希」
  与「平台识别用的指纹」共用一套语义，否则同一文件在两处算出不同结果。
- **资源领域模型（`ResourceProject` / `ResourceVersion`）**：CF / Modrinth 双平台工程与版本解析、
  `RawDependencies` 依赖字段、分页字段、缓存 JSON 互转。为什么改：这是搜索、本地扫描、
  后续 Provider 抽象的共同数据底座，必须先有稳定模型再谈接口。
- **资源搜索（`ResourceSearcher` + `FuzzySearch`）**：双站融合搜索、`IsLike` 跨站去重、
  中文经 MC 百科反查改写为英文检索词、按相似度与下载量评分排序、搜索结果不足时递归取下一页。
  为什么改：搜索是资源子系统的入口，也是 Phase 4 下载 UI 重指的前置条件。
- **本地扫描（`LocalResourceFile` + `LocalResourceScanner`）**：本地 Mod 文件双哈希识别
  （CF = 去空白 MurmurHash2 种子 1；Modrinth = SHA1）、`Display` / `Description` / `Version`
  的解析规则、递归枚举、Forge 1.13- 版本号子目录判定、同名启用/禁用去重、按文件名排序。
  为什么改：本地已装 Mod 的识别与归类是「更新检测」的前半段，先做本地半边可以不依赖网络验证。

## 优化

- **C# 侧不再反向引用主工程**：资源模型需要的运行时数据（MC 百科条目、繁简转换）改为
  静态钩子注入（`ResourceConfig`），使 `PCL.Download` 保持 net10.0 纯净，CI 与单测可在
  非 Windows 环境编译。
- **哈希计算按语义分流**：CF 指纹走 `ComputeCurseForgeFingerprint*`，通用校验走 `Compute*`，
  避免「传错枚举就静默算出另一个值」。

## 修复（开发期发现的缺陷）

> 以下均为**开发与自测过程中发现**的问题（非用户提交的 issue），按《分支与发布规范》§5.4 一并记录。
> 本版引入的模块都是新代码，这些缺陷在发布前已修掉，但仍会以「本地 Mod 认不出 / 搜索排序不对」
> 这类现象暴露给用户，故逐条写明触发条件。

- **CurseForge 指纹误删空白字节**：CF 指纹只移除 `0x09 / 0x0A / 0x0D / 0x20` 四类空白，
  若按「所有空白字符」处理会连 `0x0B / 0x0C` 一起删掉，算出的指纹与 CF 官方不一致——
  表现为本地已装 Mod 明明在 CF 上，却认不出、无法检测更新。处置：按 VB 逐字节对齐，只删这四类。
- **MurmurHash2 尾块处理照搬标准实现会算错**：标准 MurmurHash2 的尾块用 fall-through 累加，
  而 VB 原实现是 `Select Case` 无贯穿（逐项独立赋值）。直接照搬标准写法会让含 1~3 字节余量的
  文件指纹错误。处置：按 VB 的逐项语义实现，并在代码中注明二者按异或交换律等价。
- **CF / Modrinth 文件对象判别错误导致加载器丢失**：CF 的文件对象以 `gameId` 存在与否判别
  （而非按 Modrinth 的字段名猜），判别错时文件会被走 Modrinth 分支解析，`gameVersions` 里的
  加载器标记不会被读取——表现为版本列表能出、但加载器筛选（Forge / Fabric / NeoForge）全部失效。
  处置：判别条件严格按上游 `gameId`，并在单测夹具中补齐该字段。
- **跨站去重的「Drops 相等即判否」怪癖被漏掉**：VB 的 `IsLike` 在判定两站同一工程时，
  若「游戏版本 Drops 完全相同」会反判为不同（上游刻意行为）。平移时若按常理去掉这一条，
  去重结果会比 VB 多合并一类条目。处置：保留该反判逻辑，并在单测中固定其行为。
- **引擎日志整段不进 `Log1.txt`**（本版首次构建存在，本版最终制品已修复）：`PCL.Download`
  新增的日志门面类名 `Logger` 与主工程的 `MeloongCore.Logger` 同名。`NetInterop.vb` 以
  `Imports PCL.Download` 引入本程序集后，其中未限定的 `Logger.Info` 被静默解析到本类，
  C# 引擎的「开始下载 / 文件大小 / 竞速 / 换源 / 中断」等日志改写进 Console，
  用户日志中整体消失——排查时极易误判为「引擎没跑、走了 VB 回退」。
  处置：类与文件改名为 `DownloadLog`，从源头消除同名歧义（VB 侧无需逐个加命名空间限定），
  宿主注入的 `InfoSink` / `WarnSink` 接口保持公开。

## 已知问题

- **本版没有真机验证结论**（重要）：原计划的门槛「大文件分片真实触发、完整安装一次、
  游戏实际启动、NeoForge 重装回归」在本版**未执行**，整体顺延 dev.4。
  因此下载 / 安装 / 启动链路的问题无法判断是否由本版引入——遇到异常请附 `PCL/Log1.txt`。
- **C# 资源模块「已就位、未接管」**：搜索 / 版本解析 / 本地扫描的 C# 实现已通过单测，
  但主程序调用路径仍指向 VB 实现，**用户实际感知与 dev.2 基本一致**。接管要等 Phase 4。
- **资源子系统联网半边仍是 VB**：Provider 抽象、CF/MR 客户端、CF API Key 降级、
  本地文件在线反查与更新检测均未 C# 化，顺延 dev.4。
- **启动器没有内置的自动更新模块**：上游 PCL 依赖自带更新服务器，pcl-next 没有自己的更新源，
  已把更新通道整体下线——「检查更新」改为打开本项目 GitHub Releases 页面，升级需手动下载。
- **整合包导出不再附带「下载来的正式版 PCL」**：改为正式通道下复制当前启动器本体（dev 通道不附带）。
- dev 版与正式版的配置、注册表相互隔离，可与 2.99.0.1 正式版并存；
  建议升级前备份 `%APPDATA%\.PCL\`。dev 版不上传遥测。
- **构建期仍有大量 CA1416 平台兼容性警告**（数千条，集中在上游 PCL2 遗留代码调用 Windows 专有 API）：
  不影响编译产物与运行，属 .NET 10 迁移技术债，需在后续重写中逐项消除。
