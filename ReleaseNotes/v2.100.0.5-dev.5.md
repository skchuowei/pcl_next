## 重写

本版是 **Phase 4 的工程主体**：dev.4 把「数据源」全部搬进了内核，本版搬的是**数据源之后的第二层**
—— 那些既不碰 UI、也不碰下载引擎，但决定安装结果对不对的纯逻辑。

这一层此前是整条链里最不透明的部分。它不产生界面、不产生进度条，只在安装的中间过程里出现，
所以出问题时几乎不可能从现象反推：OptiFine 装到了别的目录、合并时少了一份源、
修改页认不出已装 Mod、快照版本的安装器下载 404 —— 每一个都像是「别的地方坏了」。

### 1. 安装编排的纯逻辑收进内核

新增 9 个内核文件，全部**平移**自 `ModDownloadLib` 与 `ModDownload`，不重写、不顺手改对：

| 内核文件 | 承接的原实现 | 用例 |
|---|---|---|
| `VersionMerger` | 版本 json 合并（原用 Newtonsoft `JObject.Merge`） | 14 |
| `ForgelikeInstaller` | Forge / NeoForge 安装器的参数拼装与进度解析 | 19 |
| `OptiFineInstaller` | OptiFine 安装器参数、安装所需 Java 版本探测 | 16 |
| `OptiFineProfile` | 镜像地址推导、旧式（1.8 / 1.9）版本 json 生成 | 17 |
| `LiteLoaderProfile` | LiteLoader 版本 json | 9 |
| `FabricProfile` | 实例名与 profile 地址 | 4 |
| `ForgeRecommended` | 推荐版本缓存的解析与下限回退 | 8 |
| `InstallLayout` | 安装临时目录布局、OptiFine 退化为 Mod 的判定、清单里的两条字符串规则 | 23 |
| `InstallCommitPlanner` | 修改安装的变更计划（覆盖哪些、删哪些、旧版 `resources` 要不要搬） | 15 |

九组共 125 个测试方法（`Theory` 展开后更多），连同既有用例，本版全量 **452 例**。

VB 侧同期净减 **337 行**（+273 / −610），内核新增 1428 行、测试新增 1780 行。

**版本合并的语义是这批里最容易走偏的一项**：原来用 Newtonsoft 的 `JObject.Merge`，数组是**拼接**、
来源里的 `null` 被**忽略**、对象递归合并、其余直接替换。换成 System.Text.Json 后，四条规则被逐条复现——
这里走偏不会编译报错，只会在启动时才炸，而且是「某个整合包打不开」这种无法定位的样子。

**`minecraftArguments` 的取值吸附**也保留了原样：紧跟 flag 的第一个非 flag 词吸附到该 flag 上；
同一个 flag 出现两次且取值不同时，两次都要各自绑定，不能被去重拆散。

### 2. 实例 Mod 页改由 C# 提供

dev.4 的「已知问题」第一条是「在线反查的 C# 实现已就位、未接管」。本版接管：

- **本地列表**走内核的 `LocalResourceScanner`，**在线反查**走 `LocalResourceOnlineLoader`
- `LocalResourceLoaders.vb` 从 345 行降到 139 行
- 新增 `PrimeHashes`：宿主把已经算好的 SHA1 / Murmur 指纹灌进内核，
  避免每次打开页面都把整个 `mods` 目录重读一遍（200 个 Mod 约 1~2 GB）
- 取消语义收敛到内部 `CancelState`，取消时返回 `null` 而不是抛异常 ——
  与 VB 侧「静默返回、不设输出」的旧行为一致

### 3. 整合包安装的工程批量查询

整合包安装要按 Mod 列表逐条反查工程信息，此前是 VB 侧循环调单条接口。改由 C# 的批量查询承担，
解析与错误分类复用资源子系统已有的实现。

## 优化

- **内核日志终于进了 `Log1.txt`（重要）**。GUI 宿主此前从未挂接 `PCL.Download.DownloadLog.InfoSink` /
  `WarnSink`，只有命令行前端挂过。也就是说 Phase 3 / Phase 4 陆续迁进内核的那些日志，
  **在真机上一直写进 Console，日志文件里一行都没有**。本版在 `Application_Startup` 里接上，
  位置放在资源源开关初始化之前，保证早期日志也不丢。此前凡是「让你附 `Log1.txt`」却看不到内核日志，
  都是这个原因。
- **OptiFine 源推导从两处收敛成一处**：「安装」与「另存为」各写过一遍候选源顺序，且已经开始漂移。
  合并为一个入口后，两边不可能再推导出不同的源列表。
- **CI 拆成两条线**：Windows 构建与 Linux 内核门禁原来挤在同一个 workflow 里，Ubuntu runner 慢半拍
  就把整次结论拖住；现在各自触发、各自出结论、各自重跑，重复推送还会取消旧的内核门禁 run。
- **Windows 侧补跑全部单测**：此前 452 例只在 Linux job 里跑，「Windows job 全绿」实际只等于「能编译」。
  现在 Release 配置会跑一遍，Windows 的绿才有意义。

## 修复

- **快照版本的 Forge 安装器「另存为」必定 404**：拼下载地址时漏了快照版本需要把 `-` 换成 `_` 这一步
  （`1.21.5-pre1` 在 Forge 的 maven 路径里是 `1.21.5_pre1`）。正式版走不到这条路径，所以长期没被发现。
- **OptiFine 安装所需 Java 版本的探测失败原因全部退化成同一句日志**：读 jar 内 `optifine/Installer.class`
  的头部推 Java 版本时，四种失败（文件缺失、头部不合法、版本串解析失败、IO 异常）原本都只记「探测失败」，
  排查时无法区分。现在会把具体原因带出来。
- **「installer 优先于 universal」这条规则此前没有任何用例守着**：反向验证时发现原夹具里
  installer 与 universal 从不同时出现在同一个版本条目中。这条规则错了不会报错，只会让部分 1.6.x 版本
  下到 `universal.zip`，表现为「找不到安装器」。已补夹具与用例。

### 开发期发现

- **测试用「同步阻塞」模拟慢源，在低核 runner 上会失真**：候选源竞速用 `Task.Run` 派发，
  而测试里用 `Thread.Sleep` 模拟慢源。线程池最小线程数默认等于核数，2~4 核的 CI 机器上，
  慢源会把线程占住，本该立刻完成的快源反而排队 —— 「先完成者胜」的规则没错，是快源没被调度起来。
  症状极具误导性：每次红的用例还不一样，谁先被饿到谁红。已把测试进程的最小线程数抬到 64。
- **修改安装有两处比较规则本来就不一致**：判断「新清单里有没有这一项」用区分大小写的集合，
  删除列表本身却按忽略大小写去重。这两条**没有统一**，只补了用例锁住现状 —— 统一会改变边角场景的删除行为，
  是另一个决定，不该混在迁移里做。

## 已知问题

- **下载 UI 的编排外壳仍由 VB 驱动**：本版把安装的**纯逻辑**搬进了内核（版本合并、加载器安装数据、
  目录布局、变更计划），但「把这些结果装进 `LoaderBase` / `LoaderTask` 树、由加载器树驱动进度与取消」
  仍是旧实现。`LoaderBase` / `LoaderTask` / `LoaderCombo` / `LoaderDownload` 在 32 个文件里被引用 473 处，
  改造必须先把 DTO 剥出来，属 Phase 6 的 UI 基础设施，不能塞进 Phase 4。
- **六类加载器列表仍未逐类真机安装冒烟**：dev.4 已经欠下这笔账，本版仍未清偿。逐类真正装一次
  （尤其 NeoForge 的不可下载判定、LiteLoader 的 `1.8` / `1.9` 文件名）仍待确认。
  若某类列表条目异常，请附 `PCL/Log1.txt` —— 本版起内核日志也在里面了。
- **启动器没有内置的自动更新模块**：上游 PCL 依赖自带更新服务器，pcl-next 没有自己的更新源，
  已把更新通道整体下线 ——「检查更新」改为打开本项目 GitHub Releases 页面，升级需手动下载。
- **整合包导出不再附带「下载来的正式版 PCL」**：改为正式通道下复制当前启动器本体（dev 通道不附带）。
- dev 版与正式版的配置、注册表相互隔离，可与 2.99.0.1 正式版并存；
  建议升级前备份 `%APPDATA%\.PCL\`。dev 版不上传遥测。
- **构建期仍有大量 CA1416 平台兼容性警告**（数千条，集中在上游 PCL2 遗留代码调用 Windows 专有 API）：
  不影响编译产物与运行，属 .NET 10 迁移技术债，需在后续重写中逐项消除。
