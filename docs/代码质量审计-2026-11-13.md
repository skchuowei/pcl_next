# 代码质量审计与重写记录（Windows 线 · 2026-11-13 · 进入 alpha 前）

> 审计对象：`alpha-Windows`（从 `slush` 推进，基线 `396149c`）
> 触发：用户指示「找 slush 的 bug 和代码质量太差要重写/优化的地方，然后改」
> 结论：slush 名义上完成了 VB.NET → C# 重写，但**代码实质仍是 VB 语义**（机械翻译产物）。
> 本轮先清掉零风险的兼容层字面量与 4 个真实失效 bug，其余按分期计划推进。

## 二、规模性证据：这不是「C# 代码」，是「用 C# 语法写的 VB」

| 指标 | 数量 |
|---|---|
| `using Microsoft.VisualBasic*` | 116 个文件 |
| `Conversions.*`（VB 转换函数） | 387 处 |
| `dynamic` 使用 | 339 处 |
| `Constants.vbCrLf` 等常量 | 381 处 |
| `Operators.*`（VB 晚期绑定运算符） | 111 处 |
| `My.Computer` / `My.Application` 等 | 46 处 |
| `Information.*` | 3 处 |

`dynamic` + `Operators` 的组合会**绕过编译期类型检查**，把本可在编译期发现的类型错误推迟到运行时；
`Conversions.*` 则把 C# 的显式类型规则替换成 VB 的宽松转换（`"abc"` 转整数失败返回 0 而不是抛异常），
两者叠加使「编译通过」失去意义——这正是这批代码能编译却容易运行时出错的原因。

## 三、本轮已修复

### 3.1 兼容层字面量清除（381 处 / 43 文件）

`Constants.vbCrLf` → `"\r\n"`、`vbLf` → `"\n"`、`vbTab` → `"\t"`。值完全等价，零行为变化；
保留原文件 BOM 状态与 CRLF 换行（逐文件检测后写回）。

### 3.2 网络层配置「假生效」（真 bug，2 处）

**症状**：`Application.xaml.cs` 启动时设置了 5 项 `ServicePointManager` 参数
（`Expect100Continue` / `DefaultConnectionLimit=10000` / `UseNagleAlgorithm` / `EnableDnsRoundRobin` / `ReusePort`），
并给 Win7 分支追加 `SecurityProtocolType.Ssl3`。

**根因**：`ServicePointManager` 在 .NET Core / .NET 10 上已标记过时，
**对 `HttpClient` 与 `SslStream` 完全不再生效**（微软文档明确说明设置不作用于 HttpClient）。
即这些配置从迁移那天起就一直落空，程序一直跑在默认值上；`Ssl3` 更是已被 .NET 10 移除支持（赋值可能直接抛异常）。

**修复**：
- 连接数上限迁移到 `ModNet` 两个 `HttpClient` 的 `HttpClientHandler`：`MaxConnectionsPerServer = 10000`；
- 其余四项在 `SocketsHttpHandler` 上无对应配置项，删除并注明；
- 移除 `Ssl3` 分支（Win7 回退在 .NET 10 下已无意义）。

### 3.3 正版登录「跳过 SSL 证书校验」功能从未生效（真 bug，1 处）

**症状**：`ModNet.ShouldValidateSslCertificateOnLogin(false)` 本意是让 xboxlive / minecraftservices
域名在证书错误时放行（对应上游 #3018 / #5879 的兼容处理）。

**根因**：实现挂在 `ServicePointManager.ServerCertificateValidationCallback`，且回调里
`Sender as HttpWebRequest` 取域名——.NET 10 下回调根本不会被 `HttpClient` 触发，
即便触发 `Sender` 也不是 `HttpWebRequest`（拿不到 URL），双重失效。

**修复**：改为开关字段 + `HttpClientHandler.ServerCertificateCustomValidationCallback`，
回调从 `HttpRequestMessage.RequestUri` 取主机名，按开关决定放行；默认 `true`（严格校验），
仅对 xboxlive / minecraftservices 放行，其余一律拒绝——与原始意图一致但**这次真的生效**。

### 3.4 CurseForge 搜索分页空引用（真 bug，1 处）

**症状**：`PCL.Download/ResourceSearcher.cs` 里 `requestResult["pagination"]["totalCount"]`，
当 API 响应缺少 `pagination` 节点时，先在 `null` 上取索引器 → `NullReferenceException`，
整次搜索直接失败并记为平台错误。

**修复**：先取 `pagination` 节点判空，缺失时记为 `-1`（与原 catch 分支的语义对齐）。

### 3.5 VB 字符串函数替换为原生切片（8 处）

`Strings.Left(s, n)` / `Strings.Right(s, n)` → C# range 表达式（`s[..n]` / `s[^n..]`）。
涉及资源哈希目录取前 2 位、OptiFine 版本号去 `.0` 后缀、资产列表路径拼接等。

### 3.6 异常类型成员隐藏歧义（1 处）

`MeloongCore.HttpRequestCodeException.StatusCode` 隐藏了 `HttpRequestException.StatusCode`（.NET 5+ 自带、可空），
加 `new` 并注明意图，消除 CS0108 的语义歧义（行为不变）。

## 六、结论

- **能确认的**：slush 满足「能编译、能跑」，但**不满足「是 C# 代码」**；
  本轮修掉的 4 个 bug 都属于「迁移后 API 语义变了、代码却照旧」这一类，说明同类问题还可能存在于其他 .NET Framework 专属 API 调用点。
- **下一步建议**：进入 alpha 后，把 P1 的 `dynamic` / `Conversions` 去 VB 化作为 alpha 期主线任务分批推进；
  在此之前，任何「看起来编译通过」都不能作为功能正确的证据。

## 七、追加修复：滚动惯性动画「消失」（2026-11-13 18:31）

| 项 | 内容 |
|---|---|
| 现象 | 下载页等带 `MyScrollViewer` 的列表，滚轮滚动不再有平滑惯性，一格几乎直接到位 |
| 已排除 | ① `MyScrollViewer.cs` 与原版 `MyScrollViewer.vb`（取自 `17d04a1^`）逐行比对一致：事件挂接、300 ms 时长、`AniEaseOutFluent(6)` 曲线均未在迁移中丢失；② `AaDouble(Lambda)` 的 `DoubleParam` 分支、`AniEase.GetDelta` 亦与 VB 版一致 |
| 真根因 | `ModAnimation` 动画线程每帧 `RunInUiWait → Dispatcher.Invoke` 排到 UI 线程，实测帧间隔 **124~398 ms（约 3~8 FPS**，见各版本 `PCL\Log1.txt` 的「两个动画帧间隔」）。300 ms 的 `AaDouble` 动画实际只剩 1~2 帧被执行，画面等于「瞬移」，用户感知就是「惯性动画没了」 |
| 修复 | `PerformVerticalOffsetDelta` 保留原语义（300 ms、`1-(1-t)^6` 曲线、像素增量累加、连续滚轮目标叠加），把驱动时钟换成 `CompositionTarget.Rendering`（WPF 渲染帧回调，约 60 Hz、在 UI 线程内），不再被后台动画线程的排队延迟压扁；`ScrollChanged` 在动画进行中不再回写 `RealOffset` |
| 边界处理 | 尾段（剩余 <100 ms）重开一段，避免末帧跳变；不可见/最小化时直接落位；位移 <0.5 px 时落位并退订回调，防止残留订阅与重复订阅 |
| 验证 | `dotnet build -c Release -r win-x64 --self-contained -p:PclChannel=Alpha` → 0 错误 / 14 警告；产物 `pcl-next\bin-net10\Alpha\2.100.0.7-1.06\win-x64\` |
| 遗留 | 动画线程整体帧率偏低（3~8 FPS）是全局问题，会影响所有 `Aa*` 动画的平滑度；本轮只把滚动从这条时钟摘出，全局修复（改渲染帧驱动或排查 UI 线程阻塞源）另立任务 |
