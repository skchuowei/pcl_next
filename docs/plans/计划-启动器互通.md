# 计划：启动器互通（联机大厅兼容 PCL2-CE / 陶瓦）

> 状态：实施中（2026-11-15）
> 触发需求：用户「为了扩大业务，我们要实现启动器互通（增加设置项）」，选型为「全兼容 + 一个互通开关 + 自动识别码」，
> 加入外部大厅时「自动切到对方那套加密」，同时明确「我们也要数据加密」（自建大厅不降级为明文）。

## 1 目标

1. 联机页"联机设置"新增一个"互通目标"选择（仅 pcl-next / PCL2-CE / 陶瓦），默认"仅 pcl-next"，行为不变。
2. 加入侧**自动识别**四类邀请码，不需要用户手动选格式：
   - pcl-next 自研短码：`网名9-密钥5-端口4(hex)`
   - PCL2-CE 旧大厅码：整串 Base32（大写数字码），解码后 = 8 位数字网名 + 2 位数字密钥 + 十进制端口
   - 陶瓦（Terracotta）码：25 位 Base34，5 组 5 位，第 25 位是校验位，端口藏在数值里
   - PCL2-CE 新版 `U/XXXX-XXXX-XXXX-XXXX`（Scaffolding 码，**不含端口**，需另填端口）
3. 建房侧按"互通目标"生成对应格式的码，并按该格式对应的 EasyTier 参数建网，使**同一张码两个启动器都能用**（pcl-next 自己也能解析 CE/陶瓦码）。
4. 数据加密不降级：自建大厅显式 `--encryption-algorithm aes-gcm`（等价于当前默认值，只是写死以防未来 EasyTier 改默认），从不加 `--disable-encryption`。

## 2 前置条件与阻塞项

- EasyTier 2.6.4 本地二进制已验；`--encryption-algorithm` 支持 `xor/aes-gcm/aes-256-gcm/chacha20`，`--compression` 支持 `none/zstd`，
  `--enable-quic-proxy` / `--enable-kcp-proxy` / `--use-smoltcp` / `--multi-thread` 均为布尔开关。
- **已知硬边界（必须写进 UI 提示，不能承诺双向都通）**：PCL2-CE 2.6 的建房/加入走它自己的中心服务
  （`LobbyService.CreateLobbyAsync` 先查 NAID 登录，`JoinLobbyAsync → ScaffoldingFactory.CreateClientAsync` 连服务器取端口），
  所以"CE 用户输入我们的码进我们的大厅"仍受它的服务限制；真正的互通用法是"pcl-next 用对方的码加入对方大厅"，
  以及"双方各自建房、参数与码格式对齐后网络层可互通"。
- 阻塞：无（本轮不依赖 CE 运行，验证靠启动日志核对参数）。

## 5 改动要点

### 5.1 码算法（自己实现，不复制对方代码）

- **PCL2-CE 数字码**：Base32 字符表 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`，编码一个十进制数；
  解码后按位置切：前 8 位=网名、接着 2 位=密钥、其余=端口（十进制）。生成时网名首位取 1–9，避免前导零被吞。
- **陶瓦码**：Base34 字符表 `0123456789ABCDEFGHJKLMNPQRSTUVWXYZ`（无 I/O）。前 24 位是**小端** Base34 数字，
  `value = Σ digit[i] × 34^i`；第 25 位 = `Σ digit[0..23] % 34` 的字符作校验；端口 = `value % 65536`（≥100）；
  网名 = 前 15 位，密钥 = 第 15–24 位（含校验位）——与对方解析完全一致。展示按 5-5-5-5-5 分组。
  生成时 `value = port + k×65536`（k 随机），保证端口正确且其余位随机。
- **`U/` 码**：21 位，`U/` + 16 位 Base34（4-4-4-4，跳过连字符）+ `% 7 == 0` 校验；
  网名 = `scaffolding-mc-` + 码内第 0–8 位，密钥 = 第 10 位起（与对方实现一致，含连字符）。**码内无端口**，
  加入时要求用户另填端口（借"直连地址"里的端口，未填则明确报错）。
- 我们只解码/编码**字符串格式**，不引入对方任何源码或数据集。

### 5.2 大厅档案（`LobbyTarget`）

| 档案 | 全名 | 密钥 | 覆盖 IP | 加密 | 压缩 | 兼容开关 |
|---|---|---|---|---|---|---|
| PclNext | `pclnext-`+9 | 5 位 | 10.114.114.114 | `aes-gcm`（显式写死） | 不设（none） | 否 |
| CeLegacy | `PCLCELobby`+8 | `PCLCEETLOBBY2025`+2 | 10.114.51.41 | `chacha20` | `zstd` | 是 |
| Terracotta | `terracotta-mc-`+15(小写) | 10 位 | 10.144.144.1 | `chacha20` | `zstd` | 是 |
| CeScaffold | `scaffolding-mc-`+9 | 码内 9 位 | 10.114.51.41 | `aes-gcm` | `zstd` | 是 |

"兼容开关"= `--enable-quic-proxy --enable-kcp-proxy --use-smoltcp --multi-thread`（对方固定加，缺了只是性能/路径差异，加上更贴近）。

### 5.3 会话流程

- `CreateAsync(port)`：读 `LinkInteropTarget`（0/1/2）→ 生成对应档案与邀请码；房主 `-i <档案覆盖 IP>`，白名单仍是 MC 端口。
- `JoinAsync(code)`：先按 pcl-next 码试，再按 CE 数字码、陶瓦码、`U/` 码依次试；成功后按档案参数建网，
  端口转发指向 `档案覆盖 IP : 码内端口`。端口未知（`U/` 码）时用直连地址里的端口，仍无则报错说明。
- 退出时恢复：档案字段清零，不影响下一次（每次建连重新读取设置）。

## 十一、对齐 PCL2-CE 现行 U/ 码与 Scaffolding 流程（2026-11-15 修订）

### 11.1 触发与结论

用户实测：CE 联机页的邀请码占位文本是 `编号应该长得像这样： U/NNNN-AAAA-SSSS-EEEE`，并明确"之前那个发错了"。
读 CE 源码确认了技术根因：**CE 的加入流程已经完全不经过旧数字码路径**——
`LobbyController.LaunchClientAsync` 一律走 `ScaffoldingFactory.CreateClientAsync(username, code, LobbyType.Scaffolding)`，
后者只认 `LobbyCodeGenerator.TryParse`（U/ 码）；`LobbyInfoProvider.ParseCode` 里虽然还留着 Base32 数字码分支，
但那条路径在加入/建房里都不可达。所以第 5.2 节按"CE 旧数字码"生成的码实际已失效。

由此两条旧判断被证伪（只标不删，保留追溯）：

- 第 5.1 节"Scaffolding 码要配对方中心服务才有意义，故不生成"→ **错误**。Scaffolding 是自托管协议：
  房主自己跑协议服务，房主的 EasyTier 主机名里带协议端口，没有中心服务。
- 第 10.5 节"对方启动器建房/加入走它自己的大厅服务，所以对方主动加入我们仍受其服务限制"→ **错误**，
  同一张 U/ 码双向都通（对方码我们加入、我们码对方加入）。

### 11.2 CE 侧机制档案（对齐依据，全部读自 CE 源码）

**邀请码**（`PCL.Core/Link/Scaffolding/LobbyCodeGenerator.cs`）：

| 项 | 规则 |
|---|---|
| 字符表 | `0123456789ABCDEFGHJKLMNPQRSTUVWXYZ`（`I`→1、`O`→0，共 34 位） |
| 载荷 | 16 位 Base34，小端（低位在前） |
| 校验 | 数值对 7 取模必须为 0 |
| 展示 | `U/` + 4 组 4 位、组间连字符，总长 21，连字符只在索引 4/9/14 |
| 网名 | `scaffolding-mc-` + 载荷 `[0..9]`（含第 4 位连字符，共 9 位） |
| 密钥 | 载荷 `[10..]`（9 位 `XXXX-XXXX`） |
| 端口 | **码内没有端口**，由 Scaffolding 协议索取 |

**房主启动**（`EasyTierEntity._BuildProcessAsync(true)`）：`--no-tun --multi-thread --enable-kcp-proxy --enable-quic-proxy
--encryption-algorithm aes-gcm --compression zstd --default-protocol <配置> --network-name/--network-secret 从码切
--machine-id <LauncherId> --rpc-portal <随机> --private-mode true --p2p-only`，另加 `-i 10.114.51.41`、
`--hostname "scaffolding-mc-server-<scfPort>"`、`--tcp-whitelist/--udp-whitelist <scfPort>` 与 `<MinecraftPort>`、
`-l tcp://0.0.0.0:0 -l udp://0.0.0.0:0`；中继用 `-p` 一串公共节点。

**加入流程**（`ScaffoldingFactory.CreateClientAsync`）：起 EasyTier（`-d`、`--tcp-whitelist 0 --udp-whitelist 0`）→
轮询 `easytier-cli -o json peer list` 找 hostname 以 `scaffolding-mc-server-` 开头的房主 →
`hostInfo.HostName[22..]` 即协议端口 → `AddPortForwardAsync(hostIp, scfPort)` 得到本地端口 →
TCP 连 `127.0.0.1:<本地端口>` → 先发 `c:player_ping` → 再发 `c:server_port`（2 字节大端 ushort）→
把 `hostIp:<mcPort>` 转发到本地给 MC 用。

**协议帧**（`ProtocolWriter` / `ProtocolReader` / `ScaffoldingServer._TryParseFrame`）：
请求 `[1 字节类型长度][类型][4 字节大端正文长度][正文]`；
应答 `[1 字节状态][4 字节大端正文长度][正文]`，状态 0 成功 / 32 参数错误（255 表示正文是错误字符串）；
服务端限制类型长度 ≤128、正文 ≤65536，类型用 UTF8 解码。

**类型与载荷**：`c:ping`（回显正文）、`c:protocols`（5 个类型名以 `\0` 分隔）、
`c:server_port`（空请求 → 2 字节大端端口，端口为 0 时回 32）、
`c:player_ping`（JSON `name`/`machine_id`/`vendor`，snake_case；`machine_id` 为空回 32；成功回空正文）、
`c:player_profiles_list`（JSON 数组，`kind` 字符串枚举 `HOST`/`GUEST`）。CE 客户端每 5 秒发一次心跳。

### 11.4 参数对齐要点

- Scaffolding 目标**不加 `--use-smoltcp`**：CE 走 `--no-tun` + 白名单 + 端口转发，用户态协议栈反而会让
  `127.0.0.1` 的转发建立不起来；其余兼容开关（quic/kcp/multi-thread）与 CE 一致。
- Scaffolding 目标额外加 `--p2p-only`，与 CE 的 `--private-mode true --p2p-only` 对齐。
- 房主主机名不可自定义（对方要取 `[22..]` 当端口）；「显示名」只作用于大厅玩家列表。
- 邀请码里的网络名/密钥已带好前缀，`--network-name` / `--network-secret` 直接传。
