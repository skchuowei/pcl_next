# 计划-多源并行下载

> 制定日期：2026-11-22　状态：实施中
> 触发需求：「小 mod 文件从多个镜像源分别下载；大文件、单源下载慢时从多源同时下载」

## 1. 目标

同一文件的多个分块可以同时分配给**不同下载源**并行下载，从而：

- 小/中型文件（1 MB 以上）不再被「首包竞速赢家」独占成一个源，官方 CDN 与镜像的带宽可以叠加；
- 大文件遇到单源慢时，其他源能接手新分块（而不是只能整体换源重来）；
- 慢源自动降级，不再拖累整体速度。

可验证标准：

1. 两个源参与时，两个源都收到分块请求，总吞吐高于单源；
2. `MultiSourceParallel=false` 时行为与当前版本一致（只用一个源）；
3. 校验失败仍走整文件重下，合并逻辑不变（按 `Start` 排序拼装，与源无关）。

## 2. 前置条件与阻塞项

- 依赖已完成的「主机并发分档」（`MaxChunksPerHostUnrestricted`）与「单文件分块上限」`MaxChunksPerFile`；
- 无外部阻塞。Moogle/MCIM 镜像与官方 CDN 的文件内容一致，由 sha1 校验兜底。

## 3. 现状分析

- `FileTask.TryBeginChunk` 追加分块时调用 `GetSplitCapableSource` 选源，本意已是「活动分块最少的源优先」；
- 但其中有一条硬过滤：`FileSize <= 32MB` 且发生过首包竞速时，**只允许竞速赢家参与**追加分块。
  这条规则本意是避免把分块压到已知更慢的源（真机 NeoForge installer 踩过），副作用是 ≤32MB 的文件（绝大多数 Mod）
  永远只有一个源在工作，镜像带宽完全闲置；
- `DownloadSource` 只记录 `HedgeWins/HedgeLosses`（首包胜负），没有「实际吞吐」样本，选源无法判断谁是慢源；
- `IsNoSplit` 硬编码 1MB：1MB 以下走内存缓存单线程，这块保持不变（内存路径与续传语义耦合，改动收益极小）。

## 4. 改动文件清单

| 文件 | 改动 |
|---|---|
| `PCL.Download/Models.cs` | 新增 `MultiSourceParallel`、`MultiSourceMaxSources`、`MultiSourceSlowSourceBytesPerSecond`；`DownloadSource` 增加 `SpeedEwma` / `SpeedSampleBytes` / `SpeedLock` |
| `PCL.Download/DownloadFileTask.cs` | 重写 `GetSplitCapableSource`（多源并行 + 慢源降级 + 参与源数上限）；新增 `UpdateSourceSpeed`；分块收尾时更新源速度 |
| `PCL.Download.Tests/DownloadEngineTests.cs` | 新增多源并行正/反两个用例 |
| `pcl-next/Modules/Base/NetInterop.cs` | 读取 `ToolDownloadMultiSource` / `ToolDownloadMultiSourceMax` 设置 |
| `pcl-next/Pages/PageSetup/Settings.cs` | 注册两个设置项 |
| `pcl-next/Pages/PageSetup/PageSetupDownload.xaml(.cs)` | 下载页新增「多源并行下载」开关与「参与源数」滑块 |

**明确不做**：

- 不改 `IsNoSplit`（<1MB 仍单线程内存下载）；
- 不改首包竞速本身（仍用两个源抢首块，赢家继续首块，只是后续分块不再独占）；
- 不做「文件级源预分配」（不跨文件轮转源，以免破坏「官方优先」设置语义）。

## 5. 改动要点

### 5.1 选源策略（`GetSplitCapableSource`）

候选 = 未失败、未 `RangeUnsupported`、未被 `NoSplitHostKeywords` 排除的源。

排序键（多源并行开启时）：

1. **慢源降级**：已有可信样本（`SpeedSampleBytes ≥ 1MB`）且 `SpeedEwma < MultiSourceSlowSourceBytesPerSecond`（默认 48 KB/s）的源排到最后；
2. **负载均衡**：当前活动分块数少的源优先（保证每个源都铺开）；
3. **实际吞吐**：`SpeedEwma` 高的优先（未知样本视为 0 力度，不奖不罚）；
4. **首包胜负**：`HedgeWins` 高、`HedgeLosses` 低优先；
5. `Id` 小的优先（稳定）。

参与源数上限：活动中分块涉及的不同源数达到 `MultiSourceMaxSources` 时，新分块只在已参与的源里挑（避免一次下载铺到 5+ 个源、连接过于分散）。

`MultiSourceParallel=false` 时退回旧策略（竞速赢家独占 + 首包胜负优先）。

### 5.2 源速度样本（`UpdateSourceSpeed`）

分块结束（Finished/Canceled）时计算 `chunk.Done / (TickCount64 - chunk.InitTime)`，
样本门槛 `Done ≥ 256KB && 耗时 ≥ 1s`，对 `SpeedEwma` 做 0.7/0.3 加权，并累加 `SpeedSampleBytes`。
样本只用于排优先级，不参与判死（判死仍走失败计数）。

### 5.3 设置项

- `ToolDownloadMultiSource`（bool，默认 true）
- `ToolDownloadMultiSourceMax`（int，默认 4，滑块 2~8）

## 6. 回归影响面

- 首包竞速相关用例（`Hedge*`）与 `NoSplitHostKeywords` 用例不受影响（前者走单源竞速，后者被关键字排除在候选外）；
- 断点续传、慢速换源、判死、合并、校验逻辑均不改；
- 风险点：多源并行会让镜像分到分块，镜像 403 限流可能增多 —— 由既有「403 冷却 + 迭代禁用」兜底；
  若线上出现 429 风暴，可把 `MultiSourceParallel` 关掉或把 `MultiSourceSlowSourceBytesPerSecond` 调高。

## 7. 验证步骤

1. `dotnet test PCL.Download.Tests -c Release -r win-x64`（全量，当前 570 例，新增 2 例）；
2. `dotnet build PCL.Cli` + `pclcli download --file <多源请求>` 对比单源/多源耗时
   （Modrinth 官方 + MCIM 镜像构造 2 源请求，20 个小文件 + 1 个大文件）；
3. `scripts/Build.ps1 -Channel Dev -Rid win-x64` 构建 GUI，设置页确认开关与滑块存在、默认 true/4。

## 8. 回滚方案

引擎侧改动集中在 `GetSplitCapableSource` 与新增方法；回退时只需把 `MultiSourceParallel` 默认改为 `false`
（或删掉该方法内的并行分支），即可恢复旧行为，无数据结构变更、无归档影响。
