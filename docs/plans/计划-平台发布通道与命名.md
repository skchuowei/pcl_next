## 3. 现状分析（为什么必须改）

**根因：09:39 裁决只解决了「要不要两条平台分支」，没有解决「这两条线怎么发版」。**

| # | 现状 | 问题 |
|---|---|---|
| A | `release.yml` 的 `on.push.tags` 只有 `v*`，而 §0A / §0B 又禁止平台线打 `v*` tag | 两条平台线**规则上可发、工程上发不出去**；这是本轮最主要的缺口 |
| B | §0A.2 写「接收 `feat/*` 直连 PR（短期分支目标只能是 dev）」，§0B.1 却允许 `feat/linux-*` | 同一份规范里 android 与 linux 的短期分支规则互相矛盾 |
| C | §1.7 的 `target` 固定为 `dev/slush/alpha/beta/rc` | 平台修复分支没有合法目标值 |
| D | `build.yml` 把 `android` / `linux` 都折成 `Dev` 渠道，`PclChannel` 六值 `ValidateSet` | 若给平台另起 `Linux` / `Android` 渠道，会同时破坏 §3.2 代号语义、§5.2 单号段表与 `PclTreePathGuard` |
| E | `git describe --tags`（无 `--match`） | 新增平台 tag 后，`android/v2.100.0.4-1` 会被当成最新标签，§6.2 阶段判定与 artifact 名同时误判 |
| F | 合规前置目前只写在文档里 | 没有机械护栏；一旦有人误推平台 tag 就可能直接对外分发 |

历史踩坑沿用：AGENTS §0.3.1「同一份护栏写两遍迟早漂移」，所以本轮把 tag 命名空间、通道、代号区分**集中到 §0C 一处**，不在 §0A / §0B 各写一套。

## 5. 改动要点（逐文件）

### 5.1 分支命名（§0C.1）

四类互不重叠：代号长期（六个）、平台长期（两条）、主线短期（`feat/<module>-*` / `fix/<target>-*`）、
**平台短期（`feat/linux-*` / `fix/linux-*` / `feat/android-*` / `fix/android-*`）**。

- 平台前缀即目标声明：从对应平台长期分支拉出、合回同一分支，禁止跨到 `dev` / 代号阶梯 / 另一条平台线。
- 禁止 `feat/linux/...` 二级斜杠与 `linux-feat-*` 前缀倒置（与现有扁平 `feat/*` 命名空间冲突）。
- 历史分支（`feature/loader-download-engine-port` 等）按 §九「只标不删」不追溯重命名。

### 5.2 代号区分（§0C.2）

**二维，不扩容**：代号轴六个值仍由用户决定（§3.2 D1）；平台轴 `win` / `linux` / `android` 由构建时推断。
通道标识 `dev` / `dev-linux` / `dev-android` 是**同一代号在三个端的通道**，不是三个代号。
平台差异全部落在 RID 段、制品名后缀、`PclPlatform`，三段树 `<代号>` 段形状不变 → `PclTreePathGuard` 与
`Set-VersionInfo.ps1` 的 `ValidateSet` 都不用放宽。

### 5.3 Tag 命名空间（§0C.3）

| 层 | 格式 | 触发发布 |
|---|---|---|
| 主阶梯 | `v<版本名>[-<代号>.<序号>]` | ✅ Windows |
| Linux 同步指针 | `linux/v<版本名>[-<代号>.<序号>]` | ✅ Linux 附件 |
| Android 独立发布 | `android/v<内核版本>-<N>` | ✅ 独立 Release |
| 平台归档/里程碑 | `linux/<名称>`、`android/<内核版本>-<N>` | ❌ |

带 `linux/` / `android/` 前缀的发布 tag 不会被 `v*` 匹配（要求以 `v` 开头），因此不占 §5.3 命名空间，
也不改变 §6.2 的阶段判定——前提是 `git describe` 加 `--match 'v*'`。

### 5.4 `release.yml`（本轮唯一的代码改动）

- 触发器新增 `linux/v*` / `android/v*`。
- **主 job 加排除条件**：`!startsWith(github.ref_name,'linux/') && !startsWith(github.ref_name,'android/')`。
  不加这一步，推平台 tag 会连带跑一遍 Windows 发布，把 `linux/v2.100.0.4-dev.4` 当成版本标签解析并创建错误 Release。
- `release-linux`：校验同名主 tag 存在（`git rev-parse`）→ 编译内核 + CLI + xUnit + `selftest-offline` →
  打 `linux-x64` tar.gz → 上传 workflow artifact → **gate 开启时**用 `gh release upload` 把附件挂进同名主 Release。
- `release-android`：解析 `android/v<内核版本>-<N>` → 检测 Android 工程是否存在（`ready`）→
  不存在则只写 `channel-manifest.json` 并上传 artifact（不挂必过门禁）→ **gate 开启且 ready 时**建独立 prerelease Release。
- 合规 gate 读 `vars.PLATFORM_RELEASE_ENABLED`，默认未设 = 关闭；关闭时两个 job 都只上传 artifact，
  不创建 / 修改任何 GitHub Release。

### 5.5 待执行的代码侧配套

见 §4 表格。`Set-VersionInfo.ps1` 只新增 `-Platform` 参数，**不碰** `-Channel` 的六值 `ValidateSet`
与 `$Offset` 号段表；`Directory.Build.props` 只新增 `PclPlatform` 属性，**不碰**三段树公式与护栏。

## 6. 回归影响面

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 新增 tag 触发器让 Windows 主流程被误触发 | 创建错误 Release / 版本常量写错 | 主 job 排除条件 + §7 第 3 步回归验证 |
| `git describe` 取到平台 tag | §6.2 阶段判定、CI artifact 名误判 | `--match 'v*'`（待执行）+ §0C.3 反模式 |
| 平台 tag 与归档 tag 混淆 | 归档 tag 误触发发布 | 归档 tag 不带 `v` 前缀，不在触发器列表 |
| 合规 gate 被提前打开 | 未获授权的非 Windows 制品对外分发 | gate 默认关闭；开启前提是 `docs/合规/` 留存书面答复 |
| 平台分支产物落进 `bin-net10\Linux\` | 破坏 `PclTreePathGuard` 与单号段表 | §0C.2 明令禁止 + AGENTS §附 反模式 |
| Windows 发布流程行为变化 | 现有 dev.1–dev.4 的 Release 复现不出来 | 主 job 只加 `if`，其余步骤一行未改 |

需新增/修改的验证：无单元测试改动；新增的是 workflow 结构与 tag 命名空间的机械校验（§7）。

## 8. 回滚方案

| 场景 | 回滚动作 | 保留内容 |
|---|---|---|
| 平台 tag 误触发、发布出错 | 删除该 tag（`git tag -d` + 远端同步）、按需删除错误 Release；主阶梯 tag 不受影响 | 主阶梯 `v*` tag 与历史 Release 全部不动 |
| `release.yml` 改动导致主流程异常 | `git revert <本轮提交>`，或把 `on.push.tags` 收回只留 `'v*'`；主 job 的 `if` 可保留（对 `v*` 恒为真） | 两份仓库外规则文档不进版本库，不受 revert 影响；按 §九「只标不删」追加留痕而非删除 |
| 合规 gate 需要紧急关闭 | 把仓库变量 `PLATFORM_RELEASE_ENABLED` 置回非 `true`；已上传的 workflow artifact 仍可追溯 | 已创建过的平台 Release 不自动删除，须按 L1–L5 单独评估 |
| 通道设计需要整体推翻 | 由用户裁决后按 §九「只标不删」追加新决定，撤销 §0C 相应条款 | 09:39 裁决（两条平台分支并存）与 §0A / §0B 不受影响 |
