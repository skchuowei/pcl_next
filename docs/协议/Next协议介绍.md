# Next 协议介绍

> 版本：v1（2026-11-27）
> 读者：想了解 pcl-next 联机大厅怎么工作、以及想让自己的启动器接进来的人。
> 配套：《Next协议规范.md》（线格式与字段）《Next协议接入指南.md》（怎么实现）《联机大厅使用协议.md》（许可与边界）

---

## 1. 它是什么

**next 协议**是 pcl-next 联机大厅的通信协议族：一张邀请码把两台电脑拉进同一个虚拟局域网，然后在网内用一套很小的控制协议交换「你是谁、服务器端口是多少、你能不能进来」，最后把 Minecraft 的 TCP 流量送进房主的服务器。

它没有中心服务器，没有账号体系，也不依赖任何一家厂商的联机云。协议是 pcl-next 自研的，**对第三方开放但仅限非商业用途**：任何人可以读取、复刻（独立重新实现），并与 pcl-next 双向互通；**对外发布的互通实现必须开源**（见《联机大厅使用协议.md》3.1、4.5 节）。

## 2. 为什么这样设计

| 现实约束 | 设计选择 |
|---|---|
| 联机最大成本是「打洞 + 组网」，自研不现实 | 直接复用 EasyTier 做承载层（不改其行为，只约定参数） |
| 邀请码要能口头念、要能贴进聊天框 | 短码 `网名5位-密钥5位-前缀8位`，只用无歧义字符集（无 `0/O/1/I/L`） |
| 端口会变（游戏重开、换实例） | 端口**不写进码里**，由房主在网内实时发布，加入者现问现用 |
| 谁都能连 MC 端口等于没有门禁 | 准入网关：先登记、再领一次性 ticket、再做挑战-应答，才放行 |
| 旧版邀请码不能作废 | 旧格式（9-5-4，端口在码里）仍可解析；新码与旧码共存 |
| 别的启动器也要能用 | 类型探测 + 「未知类型回 32」的兼容规则，扩展永远可选 |

## 3. 四层结构

```
┌───────────────────────────────────────────────────────────────┐
│ 数据面  联机包直传（可选）  HTTP GET/HEAD + Range，端口 25566   │
├───────────────────────────────────────────────────────────────┤
│ 准入面   Gate 网关         TCP 行协议：PCLGATE1 → ticket+proof │
├───────────────────────────────────────────────────────────────┤
│ 控制面   Scaffolding 大厅  自定义帧：c:ping / c:server_port …  │
├───────────────────────────────────────────────────────────────┤
│ 承载层   EasyTier overlay  网络名 pclnext-<网名>，密钥 13 位  │
└───────────────────────────────────────────────────────────────┘
```

| 层 | 谁监听 | 谁连接 | 是否必须实现 |
|---|---|---|---|
| 承载层 | EasyTier 进程（双方） | 双方互连 | **必须**（不接受 EasyTier 就无法进网） |
| 控制面 | 房主（`127.0.0.1:scaffoldPort`，由 EasyTier 白名单放行到 overlay） | 加入者（经本地端口转发连入） | 想「问端口 / 看成员 / 领 ticket」就必须；只连码内端口的旧房间可以不做 |
| 准入面 | 房主（网关端口，overlay 放行） | 加入者（本地隧道按需连接） | 房主启用网关时**必须**；房主没启用可回退直连 |
| 数据面 | 房主（25566，只读） | 加入者按需下载 | 可选 |

## 4. 一张邀请码里有什么

新格式：`K7M3Q-XB4T9-3fa8c1d0`（开启安全模式时追加 `-S`）

| 段 | 长度 | 作用 |
|---|---|---|
| 网名 | 5 位（31 字符表） | 拼成 EasyTier 网络名 `pclnext-<网名>` |
| 密钥 | 5 位（31 字符表） | 与第三段拼成 EasyTier `network-secret` |
| 前缀 | 8 位十六进制 | 随机生成，把密钥熵从约 24.8 bit 抬到约 56.8 bit；同时用于区分同名房间 |
| `S` | 1 段，可选 | 表示房主开了 EasyTier 安全模式（Noise），加入者必须跟着开 |

固定约定：房主在 overlay 内的地址固定为 `10.114.114.114`；房主的 EasyTier 主机名固定为 `pclnext-mc-server-<协议端口>` —— 加入者就是靠这个前缀找到房主、并从后缀读出协议端口的。

旧格式（`网名9位-密钥5位-端口4位十六进制`）仍然能被识别，但**不再生成**；它的端口直接写在码里，不依赖控制面。

## 5. 一次建房 / 加入的完整时序

**房主**

1. 生成邀请码与 EasyTier 参数（网络名、密钥、`-i 10.114.114.114`、加密算法 `aes-gcm`）；
2. 起 Scaffolding 服务（随机空闲端口），把主机名设为 `pclnext-mc-server-<该端口>`；
3. 在 EasyTier 白名单里只放行「协议端口、联机包端口（25566）、网关端口」，**不放行 MC 端口**；
4. 开游戏局域网后，把真实 MC 端口通过控制面 `c:server_port` 发布出去（端口变了只更新发布，不用重启网络）。

**加入者**

1. 解析邀请码 → 拉起 EasyTier 加入同一网络（`-d`，白名单全关）；
2. 在 peer 列表里找主机名前缀 `pclnext-mc-server-` → 得到房主 overlay IP 与协议端口；
3. 建一条本地端口转发，用 Scaffolding 客户端连上并立即发一次 `c:player_ping` 完成登记；
4. `c:server_port` 拿到 MC 端口；`c:gate` 拿到网关端口与 ticket（房主没启用就回退直连转发）；
5. 本地隧道就绪后，在游戏里连 `127.0.0.1:<本地端口>` 即可进服。

加入者此后每 5 秒发一次心跳（`c:player_ping` + `c:member_state` + `c:ping` 测延迟 + 拉成员列表）。被房主踢出时，服务端对心跳回状态码 255，正文以 `KICKED` 开头，加入端据此退出房间。

## 6. 兼容与互通

**同一套类型名同时服务两类对象**：

- 与 PCL2-CE 的 Scaffolding 大厅**格式对齐**（帧格式、`c:ping` / `c:protocols` / `c:server_port` / `c:player_ping` / `c:player_profiles_list` 五个基础类型、主机名 `scaffolding-mc-server-`），所以双方能在同一网络里认出彼此。差别只在主机名前缀与扩展类型。
- 与陶瓦（Terracotta）大厅的互通停在邀请码格式与 EasyTier 参数（网络名前缀、覆盖 IP、加密算法）这一层，不涉及对方的中心服务。
- pcl-next 自己的扩展（`c:gate`、`c:game_info`、`c:package`、`c:join_report`、`c:member_state`）**全部可选**：对方不认识就回状态码 32，发起方静默降级，不影响基础流程。

**升级策略**：协议不带全局版本号字段。能力发现靠 `c:protocols`（返回基础类型列表）与「未知类型 → 32」。因此第三方可以只实现基础五类型先跑通，再按需加扩展；新扩展不会破坏旧实现。

## 7. 安全模型

| 手段 | 防的是什么 | 强度 |
|---|---|---|
| 13 位 `network-secret`（≈56.8 bit，密码学随机） | 猜中网络名/密钥混进 overlay | 穷举不可行，但泄露即失效 |
| EasyTier `--secure-mode`（Noise，可选，双方一致） | 中继节点看到明文 | 由邀请码 `-S` 决定，不跟随本机设置 |
| `aes-gcm` 传输加密 | 链路上被动窃听 | 与对等端一致才握手成功 |
| Gate `PCLGATE1` 挑战-应答 | 拿到 overlay 但没走协议的裸连接 | `HMAC-SHA256(SHA256("pclnext-gate|" + secret), nonce + "|" + ticket)` |
| ticket 一次性 + 12 小时过期 + 踢人即撤销 | 凭证重放、被踢后继续连 | 单机最多 2 条会话，房主最多 64 条 |
| 握手 5 秒超时、同时最多 2 个未完成握手 | 慢速/并发握手拖垮房主 | 失败即 `DENY <reason>` |

**注意**：这些手段保护的是「联机通道」，不替代 Minecraft 服务器自身的白名单与正版验证；房主仍应自行决定是否开放离线模式。

## 8. 已知限制

1. 依赖 EasyTier 公共节点做中继/发现；双方网络都极差时可能连不上。
2. 没有房间目录与大厅列表：房间只能靠邀请码传播。
3. 房主能看到成员列表、overlay IP 与进服报错（这是功能，不是漏洞；见使用协议第 6 节）。
4. 端口的实时发布依赖控制面；只实现「码内端口」的旧房间没有成员列表与踢人能力。
5. 联机包直传是房主侧的只读单文件服务，不做清单对比与逐文件授权。

## 9. 许可速览（非商业 + 开源）

| 能不能做 | 结论 |
|---|---|
| 个人自用、免费开源项目、公益/教育、学习研究 | ✅ 允许，不收费、不用申请 |
| 读取协议、复刻实现、与 pcl-next 双向互通 | ✅ 允许 |
| 售卖、订阅、广告变现、付费功能捆绑 | ❌ 禁止 |
| 企业/工作室用于经营性业务（含收费代建代管房间） | ❌ 禁止 |
| 对外发布互通实现但不开源 | ❌ 禁止（必须公开仓库 + OSI 开源许可证，后续版本持续开源） |
| 只开源「互通所必需的部分」（编解码/网关/EasyTier 参数/成员管理），其余业务代码闭源 | ✅ 允许 |

另外四条老义务继续有效：不冒充官方、不绕过准入、不冒用 `pclnext-` 标识、不采集与再分发房间数据。完整条款见《联机大厅使用协议.md》。
