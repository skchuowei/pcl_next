## 2026-11-08 ① 「sln 编译 0 错误」在 RID 护栏下已不可用

- **现象**：`dotnet build pcl-next.sln -c Release` 报 `Directory.Build.props:120`
  「本次编译未指定真实 RID」；补 `-r win-x64` 又报 `NETSDK1134`
  「不支持使用特定 RuntimeIdentifier 生成解决方案」。
- **判断过程**：`PclRidGuard` 要求三段树的 `<运行环境>` 段必须是真实 RID（禁止 `any`）；
  而 .NET 10 SDK 不允许在解决方案级别指定 RID。两条约束在 sln 层无解，
  改查 `scripts/Build.ps1` 注释与 `pcl-next.vbproj` 的 `ProjectReference`，
  确认项目级构建会连带编译 `PCL.Download` / `PCLCS` / `MeloongCore`。
- **结论**：全量编译改用**项目级带 RID**：
  `dotnet build pcl-next/pcl-next.vbproj -c Release -r win-x64 --self-contained -p:PclChannel=Dev`，
  或走 `scripts/Build.ps1`（还会先刷新构建号缓存并断言三段树落点）。
  `pcl-next.sln` **不含** `PCL.Download.Tests`，编译绿不等于单测全绿，测试必须单跑。
- **适用边界**：仅 2026-11-08 起启用 `PclRidGuard` 的三条独立仓库；
  「`dotnet build pcl-next.sln -c Release` 0 错误」是旧计划文档的过时写法，不得再作为验收判据。

## 2026-11-08 ② 提交钩子与 `build-number.base` 不同源，会写出错误构建号

- **现象**：`scripts/git-hooks/prepare-commit-msg` 与 `post-commit` 都用硬编码锚点
  `85c17f13`，在 11-08 全新基线的仓库里不可达，退化分支按 `rev-list --count HEAD`
  算出 `0.05 / 0.06`；而 `scripts/Get-BuildSmallVersion.ps1` 按
  `build-number.base = 65`（Windows）算出 `0.69`，下一次提交应为 `0.70`。
- **判断过程**：读 `Get-BuildSmallVersion.ps1` 的 `root+base` 退化分支
  （`commits = base + max(0, rev-list --count HEAD - 1)`），与两个钩子的退化分支逐行比对，
  确认差在「继承基数」而非满百进位；`.git/hooks` 下没有安装任何钩子，所以当时提交不受影响，
  但一旦有人执行 `Install-GitHooks.ps1` 就会立刻污染提交信息与 `obj/pcl-build.small`。
- **结论**：两个模板的退化分支统一改为读 `scripts/build-number.base`：
  `prepare-commit-msg` 取 `base + 提交前 HEAD 计数`（本次提交的编号），
  `post-commit` 取 `base + (提交后 HEAD 计数 - 1)`（脚本同源值），锚点可达时保持原语义不叠加基数。
  已用 `sh -n` 与临时消息文件实测：提交前追加 `Build: 0.70`，与脚本提交后算出的值一致。
- **适用边界**：三条独立仓库各自一份模板；Linux（71）/ Android（60）基数不同，
  编号**仅本仓库内单调，三线之间不可互比**。未安装钩子时按 `AGENTS.md` §五.6
  手工执行 `Get-BuildSmallVersion.ps1` 补 `Build:` 行。

## 2026-11-08 ③ 运行中的 `pcl-next.exe` 会锁住旧构建目录的 DLL

- **现象**：项目级入口构建编译阶段 0 错误（2412 条已知 CA1416 警告），
  但复制产物时报 `PCL.Download.dll` 被占用；`Get-CimInstance Win32_Process -Filter "ProcessId=3584"`
  显示进程路径为 `pcl-next\bin-net10\Dev\2.100.0.4-0.69\win-x64\pcl-next.exe`。
- **判断过程**：确认是运行中的启动器持有**旧构建目录**里的 DLL，不是代码或 MSBuild 配置错误；
  编译目标本身（`msbuild -t:Compile`）可完整通过。
- **结论**：不代为结束用户进程。提交后构建号递增会落到新的三段目录
  （`2.100.0.4-0.70\win-x64\`），天然避开旧目录的锁；也可先关闭程序再重跑同一命令。
- **适用边界**：本地验证构建；发布制品仍需干净工作树，不能用 `.dirty` 后缀的构建充当发布件。

## 2026-11-08 ④ NeoForge 26.3.0.101 安装器「no minecraft installation」——命令行尾斜杠转义（已修复）

> 与 `pcl_x/PCL2/docs/经验与踩坑.md` 同日条目互为印证。按「只标不删」两份都保留：
> 旧 `PCL2` 是历史备份仓库，本条是**当前开发线**的记录与修复状态。

- **现象**：GUI 安装 `26.3-NeoForge 26.3.0.101`，安装器输出
  `There is no minecraft installation at: ...\TaskTemp\1273-692147"` 后返回 `false`。
- **判断过程**（代码层逐环复核）：
  1. `ModMain.vb` 的 `RequestTaskTempFolder` 明确返回以 `\` 结尾的目录（便于后面拼文件名）；
  2. `LoaderPlanAdapter.vb` 把 `Ctx.TempMcFolder` 作为 `McFolder` 传给 `McDownloadForgelikeLoader`；
  3. `ModDownloadLib.vb` 的 `ForgelikeInjector` 把 `McFolder` 原样传给
     `PCL.Download.ForgelikeInstaller.BuildArguments`；
  4. `BuildArguments` 拼出 `com.bangbang93.ForgeInstaller "<dir>\"`，而同一行的 wrapper
     `tmpdir` 已经 `PathUtils.RemoveSlashSuffix(...)` 去尾——**唯独 gameDir 漏了**；
  5. `CommandLineToArgvW` 把 `\"` 解析成字面引号，注入器 `new File(args[0]).exists()` 为 false，
     安装器第一道校验直接失败。日志里报错路径末尾那个 `"` 就是混入的字面引号。
- **结论（对旧记录的一处措辞更正）**：`\"` 里的**反斜杠被吞掉**、引号变成参数内字面字符，
  不是「反斜杠保留」。日志路径 `...1273-692147"` 既没有尾 `\`、又多一个 `"`，与该规则一致。
  根因与「去尾斜杠」的修复方向本身成立。
- **修复**：新增 `PCL.Download/InstallerArguments.QuoteDirectory`，Forge / NeoForge 与 OptiFine
  两处 `BuildArguments` 的目录参数（gameDir / user.home / jlw.tmpdir）统一去尾斜杠；
  盘符根 `C:\` 不能去尾（会退化成相对路径 `C:`），改为在引号内写 `\` 由解析器还原。
  另新增 `PCL.Download/JavaRequirement.ReadRequiredJavaMajor`，`ForgelikeInjector` 从原版版本 json
  读 `javaVersion.majorVersion`：≥22 时先精确匹配该主版本（`ClosedOpen(major, major+1)`），
  本机没有恰好这一版才放宽为 `AtLeast(major)`，**绝不回退到更低的 Java**；
  读不到字段仍走旧的 `≥8` 口径，老版本行为不变。
- **验证**：`dotnet test PCL.Download.Tests -c Release` **567 / 567 通过**（基线 541 + 26）；
  变异反证：把 `QuoteDirectory` 临时改回「不去尾斜杠」，恰好 **10 个守门用例变红**，还原后全绿。
  项目级入口构建 0 错误（2398 条既有警告）。
- **适用边界**：三条独立仓库的 `ForgelikeInstaller.cs` / `ForgelikeInjector` 起点相同，
  Linux / Android 线**尚未修复**，须各自移植，不在本次 Windows 提交内。
  真机 GUI 重跑 `26.3-NeoForge 26.3.0.101` 仍待执行（应进入 `Extracting json` /
  `Downloading libraries`；若卡在 processor 阶段再查 Java 25）。

## 2026-11-08 ⑧ CI 制品构建号 0.11 vs 本地 0.75：旧 tag 让硬编码锚点「意外可达」（已修复）

- **现象**：Release workflow 成功后，GitHub Release 附件名为 `PCL-Next-2.100.0.6-dev-0.11.exe`，
  而本地在同一 commit（`6cffa4f`）的干净检出算出 `0.75`。发布说明里写死的 `0.74` 也对不上。
  这正是架构裁决里要防的「新仓库退化成 0.0x」，只是这次只发生在 CI 侧。
- **根因**：`Get-BuildSmallVersion.ps1` 先判断硬编码锚点 `85c17f13` 是否可达，可达就走
  `rev-list --count <锚点>..HEAD`（不叠加 `build-number.base`）。CI 的
  `actions/checkout` 用 `fetch-depth: 0` 会连带拉下远端**残留的旧 tag 及其完整历史**，
  锚点在 CI 里因此可达；而新基线与旧历史**不共祖**，该 count 退化成「新基线自身的提交数」= 11 → `0.11`。
  本地对象库没有旧 tag，锚点不可达，走 `root+base` = 65 + (11−1) = 75 → `0.75`。
  「同一 commit 两种编号」不是脚本算错，是**判定分支依赖了本地引用状态**。
- **修复**：`build-number.base` 存在即代表独立新仓库，一律走 `root+继承基数` 分支
  （`$hasBase -or 锚点不可达`），不再受旧历史可达性影响；旧仓库没有该文件，锚点语义不变。
  发布说明的制品名改为 `PCL-Next-2.100.0.6-dev-<构建号>.exe` 通配，不再写死会漂移的数字。
- **复用判断**：判定「是否新仓库」要用**仓库内受版本控制的文件**，不要用「某个旧对象是否可达」
  这类依赖 clone/fetch 范围的信号；CI 与本地的 fetch 范围天然不同。
  另外，发布说明里**禁止写死构建号**——每次修复提交都会让它 +1，写死的数必然过期。
- **适用边界**：Linux / Android 线各有自己的 `Get-BuildSmallVersion.ps1` 与 base 文件，
  若其 CI 同样 `fetch-depth: 0`，需各自同步此修复。

- **结论**：① WPF `BlurEffect` 只模糊元素自身渲染内容，糊不到背后的兄弟元素；真局部毛玻璃须在侧栏层复制一份背景图（取 `ImgBack.Background` 的 `ImageBrush.ImageSource` 新建 `ImageBrush`，UniformToFill），裁剪到侧栏宽、加 `BlurEffect Radius=12` + 负 Margin 收边，再叠半透明色蒙层。② 侧栏宽度随 `PanMainLeft_Resize` 动画（`AaWidth`），副本宽度必须同步接入同一动画与直接赋值分支。③ 蒙层透明度不能直接改 `ColorCard`（它同时是右侧 MyCard 卡片底色，注释明确两侧统一）；新增独立 `ColorSidebarGlass`（浅/深主题分别给 alpha≈150），侧栏遮罩改绑 `ColorBrushSidebarGlass`。④ 无背景图时副本 `Visibility=Collapsed` 并清空 Fill，避免残留。
- **验证**：Release win-x64 本地构建 0 错误；pip 虚拟桌面启动实测，三侧栏（启动账号/实例/设置菜单）统一半透明透出柔化背景，菜单文字保持清晰。
- **适用边界**：局部副本不跟随主背景的平铺/居中适配（毛玻璃按 UniformToFill 铺满即可）；模糊半径固定 12，未挂现有「背景模糊」滑块；深色分支随 `ThemeRefresh` 走，未在深色主题做外观冒烟。- **后续纠正（2026-11-14 ⑦补）**：浅色调侧栏蒙层误写成三参 `MyColor(150,255,255)`，三参构造是 `(R,G,B)`、A 恒为 255（无 alpha），150 被当成 R 通道，结果渲染成不透明青色 RGB(150,255,255)。要带透明度必须用四参 `MyColor(A,R,G,B)`；两参 `MyColor(newA, MyColor)` 才是「改 alpha 取基色」。判定：三参只用于实色，任何半透明画刷一律四参。- **后续纠正（2026-11-14 ⑦补2）**：局部背景副本 + 局部 `BlurEffect` 的方案被用户否决——侧栏单独糊一块与右侧清晰背景割裂，且 `Performance` 模糊在实景照片上显脏发灰。最终落地：删除副本 `RectLeftBackdrop` 元素、`SyncLeftBackdrop()` 方法及两处宽度动画/直接赋值接入；侧栏只保留 `ColorSidebarGlass` 半透明色蒙层（磨砂/Mica 感）。背后是否模糊统一交给全局 `ImgBack.Effect`（`UiBackgroundBlur`），侧栏不再做独立局部模糊。
- **后续补充（2026-11-14 ⑦补3 · 多档位磨砂风格）**：用户要求“增加多种模糊，放设置中”，最终落地为**蒙层风格档位**（模糊强度仍由现有「背景模糊」滑块 UiBackgroundBlur 控制，不另开强度）。新增整窗蒙层 RectBackdropTint（ImgBack 之上、内容之下）+ 设置项 UiBackgroundBlurStyle（0 经典 / 1 通透 / 2 深色磨砂 / 3 主题亚克力），ApplyBackdropTint() 按档位 + ModSecret.ThemeNow 深浅主题算 Color.FromArgb(A,R,G,B)；同时把侧栏 RectLeftBackground.Fill 设为同色，让左侧栏与右侧间隙跟随同一全局背景蒙层，不再做左侧独立局部模糊。设置页「背景与音乐」在模糊滑块下加同范式 MyComboBox（绑定 UiBackgroundBlurStyle，MyComboBoxItem Value），BackgroundRefreshUI 同步 PanBackgroundStyle 显隐（无图隐藏）。主题切换 UiLauncherTheme.OnChanged 串接 ThemeRefresh 后再调 UpdateBackgroundAndTitleBar，使侧栏跟随深浅。ColorObject3 经 Application.Current.Resources.Contains 取强调色，取不到回退 Gray。hasImage 判据与既有 ImgBack.Background is not null 一致（背景图挂在 ImageBrush）。

## 2026-11-14 ⑧ 构建号「每次编译 +0.01」：计数必须放构建结束，发布构建必须关递增

- **现象**：同一提交下反复编译，产物目录、AssemblyInformationalVersion、制品名三者都是同一个 M.mm，目录互相覆盖；11-13 的 ContentId/Uuid 只能事后区分，编号本身不变。
- **判断过程**：目录名 OutputPath 由 MSBuild **属性求值期**读取 obj\pcl-build.small 决定，求值期不能跑 git/脚本；若在编译中途改缓存，本次构建的目录仍按旧号建，而 g.cs/制品按新号生成，出现「目录 1.22、exe 里 1.23」的脱钩。故只能**构建成功结束后**把计数 +1、把下一次的编号写回缓存，本次构建全程读同一份缓存。
- **结论**：① 编号改为 (提交数 + 本机累计编译次数) × 0.01，计数存 obj\pcl-build.seq，由 pcl-next.csproj 的 PclBuildSeqBump（AfterTargets=PclVersionedArtifact）调用脚本 -BumpSeq 递增，一次构建只加一次（-v:n 实测：一次构建里 PclBuildInfo 与 PclBuildSeqBump 各执行一次，seq 6→7）。② 制品命名改读产物自身 ProductVersion 的 M.mm 前缀，不再读缓存——缓存此时已预置成下一个号。③ 发布构建必须 -p:PclNoBump=true：双 RID 要同号、发布号要回到纯提交语义；elease.yml 已加该参数并断言两个 exe 的 ProductVersion 前缀一致。
- **验证**：连续两次 Build.ps1 → -1.23、-1.25（中间有一次并行构建插队）、每次都 +0.01；exe ProductVersion 与目录号一致；-p:PclNoBump=true 构建后计数不变（1.29/seq7 保持）。
- **适用边界**：编译次数是**本机**计数，本地号会领先 CI 与其他机器，跨机器核对产物一律用 BuildCommitFull/BuildContentId/BuildUuid；obj\ 不进版本库，换机器/新克隆从 0 起算；同一提交反复编译会在 in-net10 下各占一个目录，需按 §0.2/§七 定期清理散装产物（ReleaseArtifacts 不受影响）。另：共享工作区里有并行构建时，计数会被对方的构建推进，属预期。
- **后续纠正（2026-11-14 ⑦补4 · 整窗白层移除 + 侧栏变薄跟随全局）**：补3 的整窗蒙层 `RectBackdropTint` 经典白 A150 会把背景图整体洗成白雾，被用户否决。最终：整窗蒙层永远 Collapsed 不填色；风格色只赋给侧栏 `RectLeftBackground`，且 alpha 大幅降薄（经典浅 A70 / 深 A80，通透 A38/28，深色磨砂黑 A95，亚克力 accent A55）；无图时侧栏回退 `ColorBrushSidebarGlass` 资源。左右统一跟随底层 `ImgBack` 与全局 `UiBackgroundBlur` 模糊（`ImgBack.Effect` 整窗一层），不做左侧局部副本/局部模糊。实测：拖大模糊滑块左右间隙一起柔化；下拉四档可展开切换，深色磨砂只压暗侧栏。
- **GUI 坐标规律（computer_use_tool / cu）**：cu 坐标 0–1000；x 按宽缩放 `x1000=xpixel*1000/1920`，**y 在本机近似 1:1（直接用像素 y）**——此前按 `y*1000/1080` 换算会整体上压一行，导致反复点中「外观」而非下一行「背景与音乐」。菜单行高约 34px；MySlider 点击轨道不跳值，需拖动（或直接改 ini）。
