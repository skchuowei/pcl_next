## 2026-11-08 ① 「sln 编译 0 错误」在 RID 护栏下已不可用

- **现象**：`dotnet build pcl-next.sln -c Release` 报 `Directory.Build.props:120`
  「本次编译未指定真实 RID」；补 `-r win-x64` 又报 `NETSDK1134`
  「不支持使用特定 RuntimeIdentifier 生成解决方案」。
- **判断过程**：`PclRidGuard` 要求三段树的 `<运行环境>` 段必须是真实 RID（禁止 `any`）；
  而 .NET 10 SDK 不允许在解决方案级别指定 RID。两条约束在 sln 层无解，
  改查 `scripts/Build.ps1` 注释与 `pcl-next.vbproj` 的 `ProjectReference`，
  确认项目级构建会连带编译 `PCL.Download` / `PCLCS` / `MeloongCore`。
- **结论**：全量编译改用**项目级带 RID**：
  `dotnet build pcl-next/pcl-next.vbproj -c Release -r win-x64 --self-contained -p:PclChannel=Dev`，
  或走 `scripts/Build.ps1`（还会先刷新构建号缓存并断言三段树落点）。
  `pcl-next.sln` **不含** `PCL.Download.Tests`，编译绿不等于单测全绿，测试必须单跑。
- **适用边界**：仅 2026-11-08 起启用 `PclRidGuard` 的三条独立仓库；
  「`dotnet build pcl-next.sln -c Release` 0 错误」是旧计划文档的过时写法，不得再作为验收判据。

## 2026-11-08 ② 提交钩子与 `build-number.base` 不同源，会写出错误构建号

- **现象**：`scripts/git-hooks/prepare-commit-msg` 与 `post-commit` 都用硬编码锚点
  `85c17f13`，在 11-08 全新基线的仓库里不可达，退化分支按 `rev-list --count HEAD`
  算出 `0.05 / 0.06`；而 `scripts/Get-BuildSmallVersion.ps1` 按
  `build-number.base = 65`（Windows）算出 `0.69`，下一次提交应为 `0.70`。
- **判断过程**：读 `Get-BuildSmallVersion.ps1` 的 `root+base` 退化分支
  （`commits = base + max(0, rev-list --count HEAD - 1)`），与两个钩子的退化分支逐行比对，
  确认差在「继承基数」而非满百进位；`.git/hooks` 下没有安装任何钩子，所以当时提交不受影响，
  但一旦有人执行 `Install-GitHooks.ps1` 就会立刻污染提交信息与 `obj/pcl-build.small`。
- **结论**：两个模板的退化分支统一改为读 `scripts/build-number.base`：
  `prepare-commit-msg` 取 `base + 提交前 HEAD 计数`（本次提交的编号），
  `post-commit` 取 `base + (提交后 HEAD 计数 - 1)`（脚本同源值），锚点可达时保持原语义不叠加基数。
  已用 `sh -n` 与临时消息文件实测：提交前追加 `Build: 0.70`，与脚本提交后算出的值一致。
- **适用边界**：三条独立仓库各自一份模板；Linux（71）/ Android（60）基数不同，
  编号**仅本仓库内单调，三线之间不可互比**。未安装钩子时按 `AGENTS.md` §五.6
  手工执行 `Get-BuildSmallVersion.ps1` 补 `Build:` 行。

## 2026-11-08 ③ 运行中的 `pcl-next.exe` 会锁住旧构建目录的 DLL

- **现象**：项目级入口构建编译阶段 0 错误（2412 条已知 CA1416 警告），
  但复制产物时报 `PCL.Download.dll` 被占用；`Get-CimInstance Win32_Process -Filter "ProcessId=3584"`
  显示进程路径为 `pcl-next\bin-net10\Dev\2.100.0.4-0.69\win-x64\pcl-next.exe`。
- **判断过程**：确认是运行中的启动器持有**旧构建目录**里的 DLL，不是代码或 MSBuild 配置错误；
  编译目标本身（`msbuild -t:Compile`）可完整通过。
- **结论**：不代为结束用户进程。提交后构建号递增会落到新的三段目录
  （`2.100.0.4-0.70\win-x64\`），天然避开旧目录的锁；也可先关闭程序再重跑同一命令。
- **适用边界**：本地验证构建；发布制品仍需干净工作树，不能用 `.dirty` 后缀的构建充当发布件。
